# 작업 기록 남기기

## 왜 남기는가

이 프로젝트는 캡스톤 과제라 **결과물만큼 과정이 중요하다.** 발표와 결과보고서에서
"왜 그렇게 했는가"를 설명해야 하는데, 코드와 커밋만으로는 그 판단 근거가 남지 않는다.

기록은 나중에 세 가지로 쓰인다.

- 발표자료와 결과보고서의 재료
- 팀원이 그동안의 흐름을 따라잡는 수단
- 몇 주 뒤 "이때 왜 이렇게 정했지?"에 답하는 근거

그래서 **무엇을 했는지보다 왜 그렇게 판단했는지**가 더 중요하다.
커밋 메시지로 충분한 내용을 옮겨 적는 건 의미가 없다.

## 문서는 두 종류다 — 섞지 말 것

| 종류 | 위치 | 성질 |
|---|---|---|
| **갱신 문서** | `docs/프로젝트.md` `docs/현황.md` `docs/운영.md` | 항상 최신 상태만 담는다. 바뀌면 고쳐 쓴다 |
| **기록** | `docs/기록/YYYY-MM-DD_제목.md` | 그날의 사실이다. **한 번 쓰면 고치지 않는다** |

같은 내용을 양쪽에 두면 한쪽만 갱신되어 어긋난다.
"지금 사양은 20분"은 현황에, "20분으로 정한 날의 판단 과정"은 기록에 둔다.

## 작성 절차

### 1. 오늘 뭐가 있었는지 모은다

```bash
git -C <repo> log --oneline --since="today 00:00"
git -C <repo> diff --stat HEAD@{1} 2>/dev/null
ls docs/기록/
```

커밋 목록은 뼈대일 뿐이다. **대화에서 오간 판단·시행착오·정정이 진짜 내용**이므로
세션 맥락을 우선으로 삼고, 커밋은 빠진 것을 확인하는 용도로 쓴다.

### 2. 파일을 만든다 — 또는 이어 쓴다

`docs/기록/YYYY-MM-DD_제목.md`

제목은 그날의 핵심을 2~4 단어로. `카메라선정과배포`, `GCP구축`처럼 공백 없이 쓴다.

**오늘 날짜 파일이 이미 있으면 새로 만들지 말고 읽어서 이어 쓴다.**
하루에 두 번 이상 호출되는 일은 흔하다(오전에 한 번, 저녁에 한 번).
그때마다 새 파일을 만들면 목차가 지저분해지고, 같은 제목으로 다시 쓰면 오전 내용이 통째로 사라진다.

이어 쓸 때는 이렇게 한다.

- **먼저 기존 파일을 읽는다.** 이미 적힌 내용을 다시 적지 않기 위해서다
- 새로 한 일을 `## 한 일` 아래에 절을 추가해 붙인다
- `## 요약` 불릿과 `## 남은 문제`는 **그날 전체를 반영하도록 고쳐 쓴다**.
  오전에 "남은 문제"였던 것을 저녁에 해결했다면 거기서 빼야 한다
- 제목이 그날 전체를 못 담게 됐으면 파일명을 바꾼다(`git mv`)

**파일을 나누는 경우**는 하나뿐이다. 성격이 완전히 달라 한 문서로 묶으면
오히려 읽기 어려울 때. 그때는 `YYYY-MM-DD_제목.md`와 `YYYY-MM-DD_다른제목.md`로 둔다.
확신이 없으면 하나로 합치는 쪽을 고른다.

### 3. 양식

**쓰기 전에 `docs/기록/`의 가장 최근 문서를 하나 열어본다.**
아래 틀은 요약일 뿐이고, **실제 파일이 정답이다.** 문서가 쌓일수록 틀과 현실이 조금씩 벌어지는데,
그때 기준으로 삼아야 할 것은 이 문서가 아니라 직전 기록이다.
헤더 표기(`# YYYY-MM-DD · 제목`), 인용구 줄, 구분선 위치, 표와 불릿 쓰임새를 눈으로 맞춘다.


```markdown
# YYYY-MM-DD · 제목

> N주차 · 한 줄 요약
> (필요하면) 이후 상황이 바뀌었다는 주의 문구

---

## 요약
- 불릿 3~5개. 목차만 훑어도 그날이 파악되게
- 발표 슬라이드로 거의 그대로 옮길 수 있는 수준으로

## 배경
왜 이 작업이 필요했는가

## 한 일
(하위 절은 그날 내용에 맞게 자유롭게)

## 확인한 것
실측한 수치, 검증 결과

## 정정된 판단
틀렸던 것과 왜 틀렸는지 (없으면 이 절을 생략한다)

## 남은 문제
다음으로 넘긴 것
```

**고정은 네 개뿐이다** — `요약` `배경` `한 일` `남은 문제`.
이 넷은 어느 날 기록에도 들어간다. 나머지는 그날 내용에 따라 넣고 뺀다.

실제로 쓰인 선택 절들:

| 절 | 언제 쓰나 | 예 |
|---|---|---|
| `확인한 것` | 실측한 수치·검증 결과가 있을 때 | 거의 매번 |
| `정정된 판단` | 이전 판단이 뒤집혔을 때 | 09-20, 09-21 |
| `부딪힌 문제와 해결` | 기술적 난관을 여럿 넘었을 때 | 09-16 |
| `이날의 결론` | 분량이 많아 마무리가 필요할 때 | 09-21 |

`## 배경 — 카메라 소스를 정해야 했다`처럼 **절 제목에 부제를 붙여도 된다.**
그날 맥락이 한눈에 보이면 그렇게 한다.

억지로 칸을 채우지 않는다. 쓸 내용이 없는 절은 비워두는 것보다 빼는 게 낫다.

**주차 계산**: 첫 수업이 2026-09-03(목)이므로 그 주가 1주차다.
목요일 기준으로 끊어 계산한다. (9/10~9/16 = 2주차, 9/17~9/23 = 3주차)

### 4. 갱신 문서를 점검한다

기록만 쓰고 끝내면 갱신 문서가 낡는다. 오늘 바뀐 게 있는지 확인한다.

| 문서 | 이런 게 바뀌었으면 고친다 |
|---|---|
| `docs/현황.md` | 수집 사양, 검증된 사실, 남은 작업, 미확인 항목 |
| `docs/프로젝트.md` | 데이터 소스 명세, 접근 권한, 단계별 계획, 제약 |
| `docs/운영.md` | 배포 절차, 운영 명령, 문제 대응 |
| `docs/기록/README.md` | 목차에 오늘 문서를 추가하고, 주차 흐름 요약을 잇는다 |
| `README.md` | 폴더 구조나 카메라 수 같은 표면 정보 |

낡은 수치가 남아 있는지 훑어보는 것도 이때 한다. 예: 카메라 대수, 수집 주기, 용량 추정.

### 5. 커밋

문서 변경은 코드와 성격이 다르므로 `docs:` 타입으로 따로 커밋한다.
커밋 메시지는 한국어 Conventional Commits를 따른다(프로젝트 공통 규칙).

## 쓸 때 조심할 것

**없는 인과를 만들지 말 것.** 이게 가장 중요하다.

기록은 나중에 사실로 읽힌다. 서사가 매끄러워 보이려고 "이 실패 때문에 저 결정을 했다"
같은 인과를 지어내면, 몇 주 뒤에 그게 근거가 되어 잘못된 판단으로 이어진다.

실제로 이 프로젝트에서 한 번 일어났다. MVP 수집이 중단된 것을 "장애로 나흘치를 잃었고
그래서 교훈을 얻었다"고 적었는데, 사실은 테스트를 마치고 직접 종료한 것이었다.
계획대로 진행된 일을 실패담으로 바꿔놓은 셈이다.

확실하지 않으면 **사용자에게 묻거나, 모른다고 적는다.** 매끄러운 서사보다 정확한 기록이 낫다.

**추측한 수치를 단정하지 말 것.** 실측한 값은 그대로 적고, 추정이면 추정이라고 밝힌다.

**지난 날의 기록은 고치지 말 것.** 나중에 틀린 것이 드러나면 그날 기록을 수정하는 게 아니라,
새 기록의 "정정된 판단" 절에 적는다. 그래야 판단이 어떻게 바뀌어왔는지가 남는다.

단 **당일 안에서는 이어 쓰는 것이 맞다.** 오전 기록에 저녁 작업을 붙이고 요약을 다시 다듬는 건
수정이 아니라 그날이 아직 끝나지 않았다는 뜻이다. 날이 바뀌면 그 문서는 닫힌 것으로 본다.

## 분량

하루치가 100~200줄 정도면 적당하다. 그날 결정이 많았으면 길어져도 되지만,
커밋 메시지를 옮겨 적어 늘리는 건 의미가 없다. **판단과 근거에 지면을 쓴다.**
