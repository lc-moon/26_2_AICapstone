# 배포와 운영

> 수집기를 서버에 올려 돌리는 방법과, 돌아가는 동안 관리하는 방법.
> 용어를 모르는 상태에서도 따라올 수 있게 썼다.
> 최초 배포: 2026-09-21

---

## 1. 무엇을 한 것인가

**집 PC 터미널에서 직접 돌리던 프로그램을, 항상 켜져 있는 원격 컴퓨터로 옮기고
운영체제가 알아서 돌보도록 맡긴 것.**

```
[전]  내 PC 터미널 ──직접 실행──> 수집기
      창을 닫으면 끝. PC가 절전돼도 끝. 몇 달을 돌리기엔 맞지 않는 구조

[후]  GCP VM ──systemd가 관리──> 수집기
      내 접속과 무관하게 동작. 죽으면 자동 재시작. 재부팅해도 자동 시작.
      상태는 Discord로 보고받는다
```

### 용어

| 용어 | 뜻 |
|---|---|
| **VM (가상 머신)** | 구글 데이터센터에 있는 컴퓨터 한 대를 빌린 것. 우리 것은 미국 오리건(us-west1)의 `e2-micro`. 꺼두면 요금이 거의 안 나간다 |
| **SSH** | 멀리 있는 컴퓨터에 명령을 입력하는 통로. GCP 콘솔의 `SSH` 버튼을 누르면 브라우저에서 바로 열린다 |
| **git clone / pull** | GitHub에 올려둔 코드를 VM으로 내려받는 것. **GitHub이 내 PC와 VM 사이의 다리** 역할을 한다 |
| **venv (가상환경)** | 파이썬 라이브러리를 프로젝트별로 따로 담아두는 폴더. 시스템 전체를 건드리지 않아 충돌이 없다 |
| **`.env`** | 인증키를 담은 파일. 저장소가 public이라 **git에 올리지 않으므로** VM에 따로 전달해야 한다 |
| **systemd** | 리눅스의 프로그램 관리자. "서비스로 등록"한다는 건 *"이 프로그램을 계속 돌봐줘"* 하고 운영체제에 맡기는 것 |

### systemd에 등록하면 달라지는 것

| 설정 | 효과 |
|---|---|
| `enabled` | 서버가 재부팅돼도 자동으로 다시 시작 |
| `Restart=always` | 프로그램이 죽으면 30초 뒤 알아서 재시작 |
| `StandardOutput=append` | 출력을 로그 파일에 계속 기록 |

이 덕분에 SSH 창을 닫아도, 노트북을 꺼도 수집은 계속 돈다.

## 2. 배포 절차

처음부터 다시 하거나, 다른 서버에 올릴 때 이 순서대로 하면 된다.

### 2-1. VM 시작
GCP 콘솔 → **Compute Engine → VM 인스턴스** → `cctv-collector` → **시작/재개**

> 시작하면 외부 IP 요금이 붙는다(월 약 $3.65). 수집하는 동안은 계속 켜둔다.

### 2-2. SSH 접속
인스턴스 목록에서 **SSH** 버튼 → 브라우저 터미널이 열린다.

### 2-3. 코드 받기
```bash
cd ~ && git clone https://github.com/lc-moon/26_2_AICapstone.git
# 이미 받아둔 상태라면
cd ~/26_2_AICapstone && git pull
```

### 2-4. 라이브러리 설치
```bash
~/venv/bin/pip install -r ~/26_2_AICapstone/requirements.txt
```

### 2-5. `.env` 전달

**git에 없으므로 반드시 따로 넣어야 한다.** 두 가지 방법.

- **파일 업로드**: SSH 창 우측 상단 **⚙️ → 파일 업로드**. `.env`는 숨김 파일이라 파일 선택 창에 안 보일 수 있으니, 보이는 이름(`env_upload.txt` 등)으로 사본을 만들어 올린 뒤 옮긴다
  ```bash
  mv ~/env_upload.txt ~/26_2_AICapstone/.env && chmod 600 ~/26_2_AICapstone/.env
  ```
- **직접 입력**: `nano ~/26_2_AICapstone/.env` → 붙여넣기는 `Ctrl+Shift+V` 또는 우클릭
  (nano의 `Ctrl+U`는 시스템 붙여넣기가 아니다. `cutbuffer is empty`가 뜨는 이유)

**넣은 뒤 반드시 길이를 대조할 것:**
```bash
awk -F= '{printf "  %-22s %d\n", $1, length($0)-length($1)-1}' ~/26_2_AICapstone/.env
```
```
UTIC_API_KEY           40
AIRKOREA_API_KEY       96
DISCORD_WEBHOOK_URL   124
```
한 글자만 잘려도 API가 `등록되지 않은 서비스키`를 뱉는데, 그 메시지만으로는
키가 틀린 건지 승인이 안 된 건지 복사가 잘못된 건지 구분되지 않는다. 대조는 5초면 된다.

### 2-6. 시간대
```bash
sudo timedatectl set-timezone Asia/Seoul
```
수집 데이터에는 영향이 없다(코드가 한국 시각을 직접 계산한다). 시스템 로그를 볼 때 헷갈리지 않으려는 용도.

### 2-7. 동작 확인
```bash
cd ~/26_2_AICapstone/Collector && ~/venv/bin/python collect_cctv.py --once --limit 3
```
`카메라 주소 확보: 20대` → `저장: _test/...jpg | 960x540` 이 나오면 성공.
여기서 막히면 설치·인증키·네트워크 중 어디가 문제인지 출력으로 갈린다.

### 2-8. 서비스 등록
```bash
bash ~/26_2_AICapstone/deploy/install_service.sh
```
사용자 이름과 경로를 현재 환경에서 읽어 채우므로 직접 고칠 것이 없다.
`Active: active (running)`이 보이고 Discord에 `▶️ 수집 시작`이 오면 완료.

## 3. 일상 운영

```bash
sudo systemctl status cctv-collector     # 살아있나 확인
sudo systemctl restart cctv-collector    # 코드를 고친 뒤 반영
sudo systemctl stop cctv-collector       # 멈추기

tail -30 ~/26_2_AICapstone/data/logs/collector.log        # 최근 로그
grep 기상 ~/26_2_AICapstone/data/logs/collector.log | tail -5
wc -l ~/26_2_AICapstone/data/logs/capture_log.csv         # 누적 회차 수
df -h /                                                   # 디스크 여유
```

### 코드를 수정했을 때

```
내 PC에서 수정 → 커밋·푸시 → VM에서 git pull → systemctl restart
```

`git pull`만 하면 반영되지 않는다. **재시작까지 해야** 새 코드로 돌아간다.

### 사진과 로그를 내 PC로 받을 때

학습은 로컬 GPU에서 하므로 VM에 쌓인 사진을 주기적으로 받아 온다. **수집기는 멈추지 않는다.**
2026-10-10에 9/22~10/9분(2.9GB, 11,420장)을 이 방법으로 받았다.

**처음 한 번만** — PC에 gcloud를 깔고 VM 접속 키를 만든다.
```powershell
winget install --id Google.CloudSDK -e      # 설치 후 새 터미널을 연다
gcloud auth login                           # 브라우저에서 VM을 만든 계정으로 로그인
gcloud config set project aicapstone-509213
gcloud compute ssh lcmoony1@cctv-collector --zone us-west1-b --command "whoami"
```
마지막 명령이 SSH 키(`~/.ssh/google_compute_engine`)를 만들어 **프로젝트 공통 메타데이터에 등록**한다.
사용자 이름은 브라우저 SSH와 같은 `lcmoony1`로 맞춘다. 다르면 `~/26_2_AICapstone`이 남의 홈 폴더가 된다.

**받을 때마다** — Git Bash에서. 외부 IP는 `gcloud compute instances list`로 확인한다.
```bash
K=~/.ssh/google_compute_engine; H=lcmoony1@136.66.108.81; DATES="2026-10-10 2026-10-11"   # 받을 날짜 (오늘은 빼기)

# 1. VM에서 날짜별로 묶는다 (하루 약 180MB, 묶는 데 하루 10초 남짓)
ssh -i $K $H "mkdir -p ~/xfer && cd ~/26_2_AICapstone/data/images && for d in $DATES; do tar -cf ~/xfer/img_\$d.tar */\$d; done && cp ../logs/capture_log.csv ../logs/weather.csv ~/xfer/"

# 2. 4개씩 동시에 받고 체크섬을 대조한다
mkdir -p data/xfer && cd data/xfer
ssh -i $K $H 'ls ~/xfer' | xargs -P 4 -I{} scp -q -i $K $H:/home/lcmoony1/xfer/{} .
ssh -i $K $H 'cd ~/xfer && sha256sum *' > remote.sha256 && sha256sum -c remote.sha256

# 3. 풀고, 로그는 data/logs/vm/으로, 묶음은 양쪽에서 지운다
cd ../images && for t in ../xfer/img_*.tar; do tar -xf $t; done
mv ../xfer/capture_log.csv ../xfer/weather.csv ../logs/vm/ && rm -r ../xfer
ssh -i $K $H 'rm -r ~/xfer'
```
- 사진 장수를 `capture_log.csv`의 `success` 행 수와 맞춰 볼 것. 10/10에는 11,420장으로 일치했다
- **`gcloud compute scp`는 쓰지 않는다.** 윈도우에서는 PuTTY(pscp)로 돌아 초당 0.3MB밖에 안 나오고,
  원격 경로의 `~`도 풀지 못한다. 같은 키로 OpenSSH `scp`를 4개 동시에 돌리면 초당 약 3MB, 3GB에 20분이다
- **요금**: VM의 무료 아웃바운드는 월 1GB이고, 넘으면 Premium 등급 기준 GiB당 약 $0.12다
  ([VPC 가격표](https://cloud.google.com/vpc/pricing)). 1주일치(약 1.2GB)씩 받으면 월 수백 원 수준.
  우리 VM의 등급과 한국행 단가는 직접 확인하지 않았다

### 학습용 표(labels.csv)를 만들 때

수집기를 멈추지 않는다. `build_labels.py`는 수집 로그만 읽는 별도 프로그램이다.

```
1. VM에서 data/logs/capture_log.csv를 내려받는다 (위 절차를 따르면 data\logs\vm\에 온다)
2. 내 PC에서 실행
   python Tools\build_labels.py --log data\logs\vm\capture_log.csv --check-weather data\logs\vm\weather.csv
3. 결과: data\labels\labels.csv, stations.csv
```

**오래 걸린다.** 기상 1분값을 관측소·날짜마다 하나씩 받는데, API허브 응답이 느리고 자주 끊긴다.
10/10에 새 날짜 12일분(파일 77개)을 받는 데 약 45분 걸렸다. 받은 것은 저장되므로 1주일마다 돌리면 그만큼만 받는다.
`응답이 계속 중간에 끊김`으로 멈추면 **그냥 다시 실행하면 된다.** 이미 받은 파일은 다시 호출하지 않는다.

### 새 사진으로 모델을 다시 돌릴 때 (1주일마다)

```
1. 사진·로그 받기 (위 절차)
2. python Tools\build_labels.py --log data\logs\vm\capture_log.csv
3. python Model\features.py                  새 사진만 계산
4. python Model\view_check.py                새 사진만 재고, 검토할 후보가 있으면 data\review\view_review.html을 만든다
   → 그 파일을 브라우저로 열어 제외·정상을 고르고 [결정 저장]
   → python Model\view_check.py --apply %USERPROFILE%\Downloads\view_review.csv
5. python Model\baseline.py
6. Model\view_review.csv가 바뀌었으면 커밋 (검토 결과는 저장소에 남긴다)
```

검토를 건너뛰어도 5번은 돈다. 그때는 검수하지 않은 후보를 자동 판단으로 거르고 몇 장인지 알려 준다.
자동 판단은 10/9까지의 전수 검수와 168/169장 일치했다(현황 §7 거르기).

**전부 눈으로 보고 싶을 때**(발표용 데이터 등)는 카메라별 폴더로 넘겨보는 방식이 편하다.
사진을 `{카메라}\YYYYMMDD_HHMM.jpg`로 복사해 두고, 이상한 사진을 `{카메라}\제외\{사유}\`로 복사한 뒤
`python Model\view_check.py --import-folders 그폴더`로 반영한다. 폴더에 남은 사진은 정상, `제외\` 아래는 제외로 들어간다.
2026-10-10~11에 `C:\26_2_AICapstone_external\incheon_review\`로 이렇게 했다.

**스트림 해상도가 바뀌면** view_check가 새 장면(카메라@해상도)으로 인식하고 기준 사진과 글자 가림 영역을 새로 만든다.
새 장면의 사진이 적을 때(수십 장) 만든 글자 가림 영역은 덜 정확할 수 있으니, 사진이 쌓이면 `Model\view_mask\` 의 그 장면 파일을 지우고 다시 돌린다.

VM에서 돌려도 된다. 그때는 `git pull`만 하면 되고 **재시작은 필요 없다**(수집기 코드가 아니므로).
대신 VM의 `.env`에 `KMA_HUB_KEY`가 있어야 한다.

**PM2.5는 3개월이 지나면 다시 받을 수 없다.** 첫 사진(9/22)분은 12월 중순 전에 한 번은 돌릴 것.
받은 원본은 `data\labels\raw\`에 남으므로, 한 번 받아둔 구간은 3개월이 지나도 표를 다시 만들 수 있다.

## 4. Discord 알림 읽는 법

| 알림 | 시점 | 뜻 |
|---|---|---|
| ▶️ 수집 시작 | 프로그램이 뜰 때 | 정상. 단 **자주 오면 재시작이 반복된다는 뜻** |
| ⚠️ 연속 3회 실패 | 즉시 | 그 카메라 스트림이 죽었을 가능성 |
| ✅ 복구 | 즉시 | 실패하던 카메라가 다시 찍힘 |
| 🚨 회차 전멸 | 즉시 | 개별 카메라가 아니라 **네트워크·스트림 서버 문제** |
| 🚨 기상 수집 전멸 | 즉시 | 초단기실황을 못 받았다는 뜻. 학습용 기상은 API허브에서 소급하므로 **급하지 않다** |
| 🚨 비정상 종료 | 즉시 | 예외로 죽음. 30초 뒤 자동 재시작됨 |
| 📊 일일 요약 | **매일 00시** | 전날 하루치 집계 |

### 가장 중요한 것은 "안 오는 것"

문제 알림은 프로그램이 살아 있어야 보낼 수 있다. **프로세스가 통째로 죽거나 VM이 멈추면 아무 알림도 오지 않는다.**
그래서 매일 00시에 오는 일일 요약이 **생존 신고** 역할을 한다.

> 아침에 Discord에 요약이 있으면 어제 하루 살아 있었다는 뜻이고, 없으면 그때 확인하면 된다.

**일일 요약의 숫자는 참고용이다.** 메모리에 누적하므로 하루 중간에 재시작이 일어나면 그 이전 분량이 빠진다.
정확한 기록은 `capture_log.csv`에 회차마다 한 줄씩 남는다.

## 5. 문제가 생겼을 때

| 증상 | 확인 | 해석 |
|---|---|---|
| 알림이 안 온다 | `sudo systemctl status cctv-collector` | `active (running)`이 아니면 죽은 것 |
| 재시작이 잦다 | `systemctl show cctv-collector -p NRestarts` | 0이 아니면 자동 재시작이 있었다는 뜻. 로그에서 예외를 찾을 것 |
| 프로세스가 두 개인가 | `pgrep -af collect_cctv.py` | 한 줄이면 정상 |
| 특정 카메라만 실패 | 로컬에서 같은 URL로 시도 | 로컬도 실패면 **그 카메라가 죽은 것**이지 배포 문제가 아니다 |
| 이미지가 안 쌓인다 | 로그의 `건너뜀` 수 | 야간이면 `건너뜀 20`이 정상. 낮인데 그러면 태양고도 설정 확인 |
| 디스크가 찬다 | `df -h /` | 하루 약 150MB씩 쌓인다. GCS 동기화 필요 |

> `NRestarts`는 **자동 재시작만** 센다. `systemctl restart`로 사람이 직접 재시작한 것은 세지 않는다.
> 그래서 `NRestarts=0`인데 로그에 `시작`이 여러 번 찍혀 있을 수 있다 — 크래시가 아니다.

### OpenCV 경고는 무시해도 된다

```
WARN global cap.cpp:212 open VIDEOIO(FFMPEG): backend is generally available
but can't be used to capture by name
```
스트림 열기에 실패할 때 같이 나오는 잡음이다. 원인이 아니라 증상이다.

## 6. 알아둘 제약

- **VM을 끄면 수집이 멈추고 그 시간대 이미지는 영구 손실이다.** 과거 스트림을 제공하는 곳이 없다
- **비용**: 외부 IP 월 약 $3.65 + GCS 약 $0.75. VM과 디스크 자체는 무료 티어
- **디스크**: 30GB. 4개월이면 약 18GB가 쌓이므로 **GCS 동기화와 로컬 정리가 필요하다**
- **속도**: VM이 미국 리전이라 캡처가 느리다. 로컬 1~2초 → GCP 5~7초. 20대에 약 2분이라 20분 슬롯에는 여유가 있다
- **`.env`는 git에 없다.** 서버를 새로 만들면 반드시 따로 전달해야 한다
