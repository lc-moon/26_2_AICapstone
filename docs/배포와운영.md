# 배포와 운영

> 수집기를 GCP에 올려 돌리는 방법과, 돌아가는 동안 관리하는 방법.
> 용어를 모르는 상태에서도 따라올 수 있게 썼다.
> 최초 배포: 2026-09-21 23:57 KST

---

## 1. 무엇을 한 것인가

**집 PC 터미널에서 직접 돌리던 프로그램을, 항상 켜져 있는 원격 컴퓨터로 옮기고
운영체제가 알아서 돌보도록 맡긴 것.**

```
[전]  내 PC 터미널 ──직접 실행──> 수집기
      창을 닫으면 끝. Ctrl+C면 끝. PC가 절전돼도 끝.
      → 2026-09-16 Ctrl+C로 4일치를 잃었다

[후]  GCP VM ──systemd가 관리──> 수집기
      내 접속과 무관하게 동작. 죽으면 자동 재시작. 재부팅해도 자동 시작.
      상태는 Discord로 보고받는다
```

### 용어

| 용어 | 뜻 |
|---|---|
| **VM (가상 머신)** | 구글 데이터센터에 있는 컴퓨터 한 대를 빌린 것. 우리 것은 미국 오리건(us-west1)의 `e2-micro`. 꺼두면 요금이 거의 안 나간다 |
| **SSH** | 멀리 있는 컴퓨터에 명령을 입력하는 통로. GCP 콘솔의 `SSH` 버튼을 누르면 브라우저에서 바로 열린다 |
| **git clone / pull** | GitHub에 올려둔 코드를 VM으로 내려받는 것. **GitHub이 내 PC와 VM 사이의 다리** 역할을 한다 |
| **venv (가상환경)** | 파이썬 라이브러리를 프로젝트별로 따로 담아두는 폴더. 시스템 전체를 건드리지 않아 충돌이 없다 |
| **`.env`** | 인증키를 담은 파일. 저장소가 public이라 **git에 올리지 않으므로** VM에 따로 전달해야 한다 |
| **systemd** | 리눅스의 프로그램 관리자. "서비스로 등록"한다는 건 *"이 프로그램을 계속 돌봐줘"* 하고 운영체제에 맡기는 것 |

### systemd에 등록하면 달라지는 것

| 설정 | 효과 |
|---|---|
| `enabled` | 서버가 재부팅돼도 자동으로 다시 시작 |
| `Restart=always` | 프로그램이 죽으면 30초 뒤 알아서 재시작 |
| `StandardOutput=append` | 출력을 로그 파일에 계속 기록 |

이 덕분에 SSH 창을 닫아도, 노트북을 꺼도 수집은 계속 돈다.

## 2. 배포 절차

처음부터 다시 하거나, 다른 서버에 올릴 때 이 순서대로 하면 된다.

### 2-1. VM 시작
GCP 콘솔 → **Compute Engine → VM 인스턴스** → `cctv-collector` → **시작/재개**

> 시작하면 외부 IP 요금이 붙는다(월 약 $3.65). 수집하는 동안은 계속 켜둔다.

### 2-2. SSH 접속
인스턴스 목록에서 **SSH** 버튼 → 브라우저 터미널이 열린다.

### 2-3. 코드 받기
```bash
cd ~ && git clone https://github.com/lc-moon/26_2_AICapstone.git
# 이미 받아둔 상태라면
cd ~/26_2_AICapstone && git pull
```

### 2-4. 라이브러리 설치
```bash
~/venv/bin/pip install -r ~/26_2_AICapstone/requirements.txt
```

### 2-5. `.env` 전달

**git에 없으므로 반드시 따로 넣어야 한다.** 두 가지 방법.

- **파일 업로드**: SSH 창 우측 상단 **⚙️ → 파일 업로드**. `.env`는 숨김 파일이라 파일 선택 창에 안 보일 수 있으니, 보이는 이름(`env_upload.txt` 등)으로 사본을 만들어 올린 뒤 옮긴다
  ```bash
  mv ~/env_upload.txt ~/26_2_AICapstone/.env && chmod 600 ~/26_2_AICapstone/.env
  ```
- **직접 입력**: `nano ~/26_2_AICapstone/.env` → 붙여넣기는 `Ctrl+Shift+V` 또는 우클릭
  (nano의 `Ctrl+U`는 시스템 붙여넣기가 아니다. `cutbuffer is empty`가 뜨는 이유)

**넣은 뒤 반드시 길이를 대조할 것:**
```bash
awk -F= '{printf "  %-22s %d\n", $1, length($0)-length($1)-1}' ~/26_2_AICapstone/.env
```
```
UTIC_API_KEY           40
AIRKOREA_API_KEY       96
DISCORD_WEBHOOK_URL   124
```
한 글자만 잘려도 API가 `등록되지 않은 서비스키`를 뱉는데, 그 메시지만으로는
키가 틀린 건지 승인이 안 된 건지 복사가 잘못된 건지 구분되지 않는다. 대조는 5초면 된다.

### 2-6. 시간대
```bash
sudo timedatectl set-timezone Asia/Seoul
```
수집 데이터에는 영향이 없다(코드가 한국 시각을 직접 계산한다). 시스템 로그를 볼 때 헷갈리지 않으려는 용도.

### 2-7. 동작 확인
```bash
cd ~/26_2_AICapstone/Collector && ~/venv/bin/python collect_cctv.py --once --limit 3
```
`카메라 주소 확보: 20대` → `저장: _test/...jpg | 960x540` 이 나오면 성공.
여기서 막히면 설치·인증키·네트워크 중 어디가 문제인지 출력으로 갈린다.

### 2-8. 서비스 등록
```bash
bash ~/26_2_AICapstone/deploy/install_service.sh
```
사용자 이름과 경로를 현재 환경에서 읽어 채우므로 직접 고칠 것이 없다.
`Active: active (running)`이 보이고 Discord에 `▶️ 수집 시작`이 오면 완료.

## 3. 일상 운영

```bash
sudo systemctl status cctv-collector     # 살아있나 확인
sudo systemctl restart cctv-collector    # 코드를 고친 뒤 반영
sudo systemctl stop cctv-collector       # 멈추기

tail -30 ~/26_2_AICapstone/data/logs/collector.log        # 최근 로그
grep 기상 ~/26_2_AICapstone/data/logs/collector.log | tail -5
wc -l ~/26_2_AICapstone/data/logs/capture_log.csv         # 누적 회차 수
df -h /                                                   # 디스크 여유
```

### 코드를 수정했을 때

```
내 PC에서 수정 → 커밋·푸시 → VM에서 git pull → systemctl restart
```

`git pull`만 하면 반영되지 않는다. **재시작까지 해야** 새 코드로 돌아간다.

### 로그를 실시간으로 볼 때

```bash
tail -f ~/26_2_AICapstone/data/logs/collector.log
```
`Ctrl+C`로 빠져나온다. **이건 로그를 구경하는 창일 뿐이라 수집기는 꺼지지 않는다.**

## 4. Discord 알림 읽는 법

| 알림 | 시점 | 뜻 |
|---|---|---|
| ▶️ 수집 시작 | 프로그램이 뜰 때 | 정상. 단 **자주 오면 재시작이 반복된다는 뜻** |
| ⚠️ 연속 3회 실패 | 즉시 | 그 카메라 스트림이 죽었을 가능성 |
| ✅ 복구 | 즉시 | 실패하던 카메라가 다시 찍힘 |
| 🚨 회차 전멸 | 즉시 | 개별 카메라가 아니라 **네트워크·스트림 서버 문제** |
| 🚨 기상 수집 전멸 | 즉시 | 초단기실황은 백필이 안 되므로 **그 시간대는 복구 불가** |
| 🚨 비정상 종료 | 즉시 | 예외로 죽음. 30초 뒤 자동 재시작됨 |
| 📊 일일 요약 | **매일 00시** | 전날 하루치 집계 |

### 가장 중요한 것은 "안 오는 것"

문제 알림은 프로그램이 살아 있어야 보낼 수 있다. **프로세스가 통째로 죽거나 VM이 멈추면 아무 알림도 오지 않는다.**
그래서 매일 00시에 오는 일일 요약이 **생존 신고** 역할을 한다.

> 아침에 Discord에 요약이 있으면 어제 하루 살아 있었다는 뜻이고, 없으면 그때 확인하면 된다.

**일일 요약의 숫자는 참고용이다.** 메모리에 누적하므로 하루 중간에 재시작이 일어나면 그 이전 분량이 빠진다.
정확한 기록은 `capture_log.csv`에 회차마다 한 줄씩 남는다.

## 5. 문제가 생겼을 때

| 증상 | 확인 | 해석 |
|---|---|---|
| 알림이 안 온다 | `sudo systemctl status cctv-collector` | `active (running)`이 아니면 죽은 것 |
| 재시작이 잦다 | `systemctl show cctv-collector -p NRestarts` | 0이 아니면 자동 재시작이 있었다는 뜻. 로그에서 예외를 찾을 것 |
| 프로세스가 두 개인가 | `pgrep -af collect_cctv.py` | 한 줄이면 정상 |
| 특정 카메라만 실패 | 로컬에서 같은 URL로 시도 | 로컬도 실패면 **그 카메라가 죽은 것**이지 배포 문제가 아니다 |
| 이미지가 안 쌓인다 | 로그의 `건너뜀` 수 | 야간이면 `건너뜀 20`이 정상. 낮인데 그러면 태양고도 설정 확인 |
| 디스크가 찬다 | `df -h /` | 하루 약 150MB씩 쌓인다. GCS 동기화 필요 |

> `NRestarts`는 **자동 재시작만** 센다. `systemctl restart`로 사람이 직접 재시작한 것은 세지 않는다.
> 그래서 `NRestarts=0`인데 로그에 `시작`이 여러 번 찍혀 있을 수 있다 — 크래시가 아니다.

### OpenCV 경고는 무시해도 된다

```
WARN global cap.cpp:212 open VIDEOIO(FFMPEG): backend is generally available
but can't be used to capture by name
```
스트림 열기에 실패할 때 같이 나오는 잡음이다. 원인이 아니라 증상이다.

## 6. 알아둘 제약

- **VM을 끄면 수집이 멈추고 그 시간대 이미지는 영구 손실이다.** 과거 스트림을 제공하는 곳이 없다
- **비용**: 외부 IP 월 약 $3.65 + GCS 약 $0.75. VM과 디스크 자체는 무료 티어
- **디스크**: 30GB. 4개월이면 약 18GB가 쌓이므로 **GCS 동기화와 로컬 정리가 필요하다**
- **속도**: VM이 미국 리전이라 캡처가 느리다. 로컬 1~2초 → GCP 5~7초. 20대에 약 2분이라 20분 슬롯에는 여유가 있다
- **`.env`는 git에 없다.** 서버를 새로 만들면 반드시 따로 전달해야 한다
