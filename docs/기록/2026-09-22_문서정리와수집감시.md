## 배경 — 문서가 사람을 위한 형태가 아니었다

전날까지 만든 문서 넷(`PROJECT_CONTEXT.md` `인수인계.md` `배포와운영.md` `작업요약_1주차.md`)은
각각 다른 목적으로 다른 시점에 쓰여 있었다. 문제가 셋이었다.

- **말투가 AI용이다.** "새 세션은 이 문서를 먼저 읽을 것", "Claude Code 인수인계용 문서" 같은 문장은
  프로젝트 문서가 아니라 작업 메모처럼 보인다
- **파일명만으로 순서를 짐작할 수 없다.** 무엇을 먼저 읽어야 하는지, 어느 게 최신인지 알 수 없다
- **성격이 다른 내용이 섞여 있다.** `인수인계.md` 하나에 "지금 사양"과 "그날 무엇을 했나"가 함께 있었다

세 번째가 핵심이었다. 같은 사실이 두 군데에 있으면 한쪽만 갱신되어 어긋난다.
실제로 전날 `배포와운영.md`를 만들면서 `인수인계.md`의 배포 절차를 포인터로 바꾼 적이 있는데,
같은 원칙을 문서 전체에 적용하지 않고 있었다.

## 한 일

### 문서를 두 종류로 갈랐다

| 종류 | 성질 | 파일 |
|---|---|---|
| **갱신 문서** | 항상 최신 상태만. 바뀌면 고쳐 쓴다 | `프로젝트.md` `현황.md` `운영.md` |
| **기록** | 그날의 사실. 한 번 쓰면 고치지 않는다 | `기록/YYYY-MM-DD_제목.md` |

이름도 바꿨다. `PROJECT_CONTEXT.md` → `프로젝트.md`, `인수인계.md` → `현황.md`,
`배포와운영.md` → `운영.md`. "컨텍스트", "인수인계" 같은 말은 AI에게 넘기는 문서라는 인상을 준다.

`프로젝트.md`에서는 §2 "현재 진행 상태"를 덜어냈다. `현황.md`와 완전히 겹쳤고,
그 안의 "실행 환경" 항목은 *"집 데스크탑 상시 가동, GCP 이전은 검토했으나 현재는 로컬 유지"*로
이미 사실과 달랐다. 전날 GCP에 배포했는데 문서는 그대로였던 것이다.

Phase 1 계획도 절반이 끝났거나 폐기된 항목이었다. "에어코리아 수집기 만들기"가 최우선으로
적혀 있었는데, 전날 백필이 되는 것을 확인해 **안 만들기로 결정한 항목**이다.

### 기록 폴더를 만들고 양식을 통일했다

`docs/기록/`에 날짜순으로 쌓기로 했다. 2주차 MVP 기록은 옮겨오고,
3주차 GCP 구축과 카메라 선정·배포는 새로 썼다.

세 문서가 각각 다른 구성이었다. 09-16은 기술 보고서, 09-20은 주제별, 09-21은 번호 매긴 시간순.
읽다 보면 리듬이 계속 끊겼다. 공통 뼈대로 맞췄다.

```
요약 → 배경 → 한 일 → 확인한 것 → (정정된 판단) → 남은 문제
```

**`요약`은 새로 넣었다.** 목차와 요약만 읽으면 그 주에 무엇이 있었는지 파악되고,
발표 슬라이드로 거의 그대로 옮길 수 있는 수준을 목표로 했다.

09-16 문서는 이전 세션이 쓴 원문이라 **수치는 하나도 건드리지 않고 배치만 바꿨다.**
107회차/99성공/92.5%, 실패 8건 표, 1.37초, 289KB 같은 값은 그대로다.

### 공개 저장소 고려

저장소가 public이라 두 가지를 걷어냈다.

- **팀원 실명** → 역할 표기로 (`팀 3인: 팀장 겸 AI 모델 / 프론트·백엔드 / 시각화`)
- **GCP 프로젝트 식별자와 예산 알림 이름** → `_archive/서버정보_비공개.md`로 이동

프로젝트 ID는 자격증명이 아니라 알아도 접근이 안 되지만, 굳이 공개할 이유도 없다.
실명 쪽이 더 실질적인 고려사항이었다.

### 기록을 스킬로 만들었다

매 세션 문서 작성 규칙을 설명해야 하고, 기록 남기는 것 자체를 잊기 쉽다는 문제가 있었다.

**`CLAUDE.md` 대신 스킬을 골랐다.** `CLAUDE.md`는 매 세션 전체가 컨텍스트에 올라가는데,
양식·절차·주의사항을 다 넣으면 160줄이 넘는다. 스킬은 이름과 설명 한 줄만 상시 노출되고
본문은 호출할 때만 읽힌다. 설명에 *"세션이 끝나갈 무렵 오늘자 기록이 없으면 먼저 제안할 것"*을
넣어, 별도 지침 없이도 잊지 않도록 했다.

### 오후 — 첫 하루치를 실측했다

전날 23:57에 가동했으니 이날이 첫 온전한 하루였다. 추정으로 적어둔 값들을 실제 숫자로 바꿨다.

| | 추정이었던 값 | 실측 |
|---|---|---|
| 장당 용량 | 289KB (MVP 1대 기준) | **271KB** (20대 평균) |
| 회차 소요 | "20대 × 5~7초 ≈ 2분" | **2분 23초** (124번 재시도 40초 포함) |
| 4개월 누적 | 18GB | **약 22GB** |

태양고도 게이트도 처음 실측됐다. 일출이 06:25였고 **첫 이미지가 06:40**이다.
06:20 회차는 고도 미달로 건너뛰었다. 계산이 실제와 맞았다는 뜻이다.

**`건너뜀 0`이 중요하다.** 20대 순차 캡처가 20분 슬롯 안에 여유롭게 끝난다는 확인이다.
"GCP가 미국 리전이라 캡처가 느리다"는 우려가 회차 예산을 위협하지 않는다.

### GCS 동기화를 1순위에서 내렸다

디스크는 29GB 중 3.7GB(13%) 사용, `data/`가 79MB였다.

| 시점 | 총 사용 | 여유 대비 |
|---|---|---|
| **11/11 (모델 마감)** | 13GB / 29GB | 36% |
| 1/31 (수집 종료) | 26GB / 29GB | **90%** |

누적량은 추정보다 20% 늘었는데, **그런데도 우선순위는 내려갔다.**
문제가 되는 시점이 12월 이후이고 그때는 모델 작업이 끝나 있다.
마감이 50일 남은 상황에서 급하지 않은 일에 시간을 쓸 이유가 없다.

대신 **일일 요약에 디스크 사용률을 넣고 80%에서 경고**가 오게 했다.
`df`의 `Use%`·`Avail`과 같은 기준으로 계산해, Discord 숫자와 서버에서 본 숫자가 어긋나지 않게 했다.
하루 증가량이 1%에 못 미쳐서 하루 한 번 확인으로 충분하다.

### 기상값 대체를 없앴다 — 오늘의 핵심 판단

발단은 팀장 지적이었다.

> 구할 수 없었지만 데이터가 부족해서 가까운 기상정보값이라도 썼어요~ 가 된 것 같아서.
> 결국 정확한 사진과 정확한 값으로 학습했다는 게 남아야 하는데.

확인해보니 **아직 사진에 붙이는 단계는 아니었다.** `build_labels.py`가 미구현이라
`weather.csv`에 행이 하나 더 생기는 것뿐이고, 병합 방식은 결정되지 않은 상태였다.
즉 우려한 일은 "앞으로 그렇게 짜면 일어나는 일"이었다.

**그런데 인접한 문제가 실재했다.** 직전 시간으로 대체해 성공하면 `ok`에 집계되어
로그에 `13/13`, 일일 요약에 `312/312`로 찍힌다. **14시가 비어 있는데 건강하게 보인다.**
오전에 고친 결함(결측이 드러나지 않음)과 같은 병이 성공 경로에 남아 있던 셈이다.

게시가 매시 15~40분이고 우리는 `:40`에 받으니 마감 직전이다. 게시가 `:45`로 밀리는 게 흔하면
**매시간 대체를 타면서 13/13으로 보이고** 실제로는 한 시간씩 밀린 값만 쌓일 수 있었다.

그래서 **먼저 측정했다.** `weather.csv`의 시각별 행 수를 세면 바로 나온다.

```
13 20260922 0000
13 20260922 0100
 ...            (00~11시 12시간)
13 20260922 1100
```

12시간 모두 격자 13개씩. 중복도 결측도 0건 — **대체가 한 번도 일어나지 않았다.**
게시가 `:40` 전에 안정적으로 끝난다는 뜻이고, 그렇다면 대체 경로는
아무 일도 하지 않으면서 집계를 부풀릴 위험만 들고 있는 코드였다.

**재시도를 같은 시각으로 두 번으로 바꿨다.** 이전 코드도 격자당 요청을 2번 했으므로
**요청 횟수가 그대로고 회차 소요 시간도 변하지 않는다.** 두 번째 요청의 대상 시각만 바뀌었다.

원칙은 `현황.md` §2에 박아뒀다.

> 사진에 붙이는 기상값과 PM2.5는 시각이 정확히 일치하는 것만 쓴다.
> `build_labels.py`에 최근접 시각 조인을 넣지 않는다.

방어 논리 때문만이 아니다. **기상값의 첫 용도가 필터링**(강수·고습 프레임 제거)인데,
14시에 비가 시작됐는데 13시 `PTY=0`을 붙이면 비 오는 프레임이 깨끗한 것으로 통과한다.
오차가 조금 커지는 게 아니라 **필터가 반대로 동작하고**, 그 프레임은
"PM2.5는 낮은데 시야가 흐린" 사례가 되어 모델을 거꾸로 가르친다.

### 기상 부분 실패를 알리게 했다

기상 쪽 보호가 카메라보다 얇았다. **보호가 더 두터워야 할 쪽인데.**

| | 카메라 | 기상 |
|---|---|---|
| 시간당 기회 | 3번 (20분 주기) | **1번** |
| 실패 1건의 무게 | 라벨 단위로는 손실 0 | **그 시각 영구 결측** |
| 개별 실패 알림 | 3회 연속 시 경고 | **없었음** |

전멸(13개 전부 실패)만 알리고 있었다. 13개 중 12개가 실패해도 `ok=1`이라 조용했고,
다음날 일일 요약에야 드러났다. **초단기실황은 1일치 조회가 되므로 같은 날 알면 복구가 가능한데,
감시 시점이 그 창을 넘어가는 구조였다.** 이제 `ok < all`이면 즉시 알리고 대표 실패 사유도 같이 보낸다.

**자동 보충(실패한 격자·시각을 다음 시간에 재시도)은 만들지 않았다.**
기상 데이터가 11시간치뿐이라 실패율을 모르는 상태다. 부분 실패 알림이 먼저 있으면
며칠 안에 빈도가 드러나고, 그때 필요한 모양도 정확히 알게 된다.
쓰이지 않을 수 있는 코드에 상태 관리를 먼저 붙일 이유가 없다.

### 카메라 1대 장애 — 진단 경로

`송도5교사거리(124) 3회차 연속 실패` 알림이 왔다. 자동 채점 3위(77.9점)에
육안으로도 S급이라 본 카메라라서 그냥 넘길 수 없었다.

```
1. 124만인가 전체인가   → 회차 종료 로그가 "성공 19 / 시도 20"  → 124만
2. 실패 사유            → capture_log.csv error 컬럼이 "스트림 열기 실패"
3. 주소가 바뀌었나      → url_cache.json과 현재 목록 API 응답이 동일
```

**19대가 같은 호스트(`cctv.fitic.go.kr`)에서 정상 수집되고 있다**는 점이 결정적이었다.
네트워크·DNS·호스트 장애·IP 차단·TLS가 전부 배제된다. 같은 서버에서 19개 스트림은 열리고
하나만 안 열리면, **그 스트림만 서버에 퍼블리시되지 않는 상태**다. 제공 측 카메라가 꺼진 것이다.

**기다리기로 했다.** 복구되면 복구 알림이 자동으로 온다.
MVP 때 용현사거리가 70분 끊겼다가 스트림 ID 변경 없이 스스로 돌아온 전례가 있다.

안 돌아올 경우의 방침도 정했다. **124를 빼는 게 아니라 후보를 한 대 추가한다.**
비대칭이기 때문이다 — 추가 비용은 거의 0(디스크 하루 +10MB, 회차 +6초)인데,
교체 비용은 시간이다. 카메라를 늦게 넣으면 그 카메라의 시계열이 그만큼 짧아진다.
124가 돌아오면 21대가 되고, 송도5교 화각은 버릴 이유가 없다.

### 배포 — 돌고 있는 것을 멈추지 않고 고치는 방법

수정을 위해 수집을 멈춰야 하는지가 문제였는데, **아니었다.**

**Python은 시작할 때 소스를 한 번 읽어 메모리에 올린다.** 그 뒤로 디스크의 `.py`를 다시 보지 않으므로,
돌고 있는 수집기는 `git pull`을 해도 영향을 받지 않는다. 편집에는 시간 제약이 없고
**시간에 민감한 건 `systemctl restart` 한 줄뿐이다.**

안전 구간은 회차 소요 실측(2분 23초)에서 나왔다.

```
:40  회차 시작 ─┐
:43 ────────────┘  ← 여기부터
     ...           안전 구간 (약 15분)
:58 ────────────┐
:00  다음 회차  ┘
```

12:30:47에 재시작했고 12:40 회차에 합류했다. **이미지 손실 0.**
12:20 회차는 12:22:23에 정상 마감돼 있었다.

restart가 **메모리 상태를 초기화한다**는 것도 확인했다. `fail_streak` `alerted` `day` `daily`가
모두 리셋된다. 그래서 124번 경고가 3회차 뒤에 다시 오고, 이날 일일 요약은
12:40 이후분만 집계된다. 고장이 아니라 예상된 동작이다.

부작용이 하나 더 있다. **`resolve_cameras()`는 시작할 때 한 번만 목록 API를 조회한다.**
스트림 주소가 바뀌면 돌고 있는 프로세스는 옛 주소로 영원히 실패한다.
주소 변경이 의심되면 restart가 해결책이라는 뜻이다.

## 확인한 것

**스킬은 재시작 없이 바로 인식됐다.** `.claude/skills/기록/SKILL.md`를 만들자마자
스킬 목록에 나타났다. 한글 이름도 문제없었다.

**문서 구조가 정리된 뒤 `docs/`는 이렇게 됐다.**

```
docs/
├─ 프로젝트.md      배경·가설·접근 권한·데이터 소스 명세·단계별 계획·제약
├─ 현황.md          지금 사양·검증된 사실·남은 작업·미확인 항목
├─ 운영.md          배포 절차·운영·문제 대응
└─ 기록/            2주차·3주차 (갱신하지 않음)
```

**첫 하루치 수집 실적** (06:40~11:20, 15회차 기준)

| 항목 | 값 |
|---|---|
| 15/15 달성 | **19대** |
| 124번 | 13/15 (스트림 장애) |
| 건너뜀 | **0** |
| 전체 | 298 / 300 = **99.3%** |

**기상 게시는 `:40` 전에 끝난다.** 00~11시 12시간 연속으로 격자 13개씩 빠짐없이 수집됐고,
직전 시간으로 대체된 경우가 0건이었다. 이 실측이 대체 경로를 제거할 근거가 됐다.

**배포 후 검증** — 12:40 회차에서 `기상 수집 13/13 격자 | 09-22 12시`,
`회차 종료 | 성공 19 / 시도 20 / 건너뜀 0`. 같은 시각 재시도 경로가 정상 동작한다.

## 남은 문제

**송도5교사거리(124) 복구 대기.** 제공 측 문제로 확정했으니 기다리는 것이 맞지만,
며칠 안 돌아오면 후보 카메라를 한 대 추가한다(124는 빼지 않는다).

**기상 실패율을 모른다.** 12시간이 전부 성공이라 부분 실패가 얼마나 흔한지 알 수 없다.
그중 8시간이 야간이라 표본이 부하 낮은 시간대에 치우쳐 있기도 하다.
부분 실패 알림을 넣었으니 며칠 안에 드러나고, 그 빈도를 보고 자동 보충을 만들지 정한다.

**`build_labels.py`가 다음 작업 1순위가 됐다.** 모델 작업의 입구이고,
막히면 11/11까지 아무것도 못 한다. 병합 원칙(시각 일치만)은 이미 정해뒀다.

**기록 스킬은 이번이 두 번째 사용이다.** 오전에 새로 만들고 오후에 이어 쓰면서
당일 append 규칙과 파일명 변경 규칙이 실제로 동작하는 것을 확인했다.
첫 사용 중에 드러나 보완한 것이 둘 있었다.

- 하루에 두 번 호출될 때의 동작이 정의되지 않아, 덮어쓰기로 오전 내용이 사라질 수 있었다
- 스킬에 적힌 양식과 실제 파일의 절 구성이 어긋나 있었다(`부딪힌 문제와 해결`, `이날의 결론`이 빠져 있었다).
  **직전 기록을 읽어 맞추라**는 지시를 넣어, 문서가 쌓여도 기준이 실물에 있도록 했다

그리고 **고농도 데이터 부재는 그대로다.** 문서를 정리하고 감시를 붙여도 이건 안 풀린다.
