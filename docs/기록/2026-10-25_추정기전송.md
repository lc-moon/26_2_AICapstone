## 배경

같은 날 서비스 세션에서 역할을 확정하고(A 백엔드 김승진, B 프론트 박금혁), 승진 님의 백엔드 PR #2(수신·격자 계산·조회 API)를 리뷰해 머지했다.
받는 쪽이 생겼으니, 이제 보내는 쪽을 만들어야 했다. 추정기는 지금까지 `data/estimates/estimates.csv`와 결과 페이지에만 값을 남겼다.

조건은 사용자가 처음에 정해 주었다.
- 백엔드는 아직 배포 전이다. 주소·토큰이 비어 있으면 전송을 건너뛰어야 한다
- 전송이 실패해도 추정과 파일 저장은 그대로 간다
- 시각이 안 맞는 값을 메우지 않는 원칙(현황 §2)은 그대로다. null은 null로 보낸다
- 설계 갈림길은 구현 전에 묻는다

### 만든 것

- **`Estimator/send.py`** — CSV 한 줄을 응답 예시(`shared/mock/ingest_estimates.json`)와 같은 모양의 행으로 바꿔 보낸다
  - 회차(`slot`)는 촬영 시각을 20분 단위로 내린 값이다. 조원 자료를 만든 `Tools/make_service_shared.py`와 같은 규칙이다
  - `rain` 칸은 `60분 0.0mm · 레이더 1.2mm/h` 같은 글자라 60분 강수량 숫자만 `rain_60m`으로 읽는다. 결측이나 빈칸이면 null
  - 빈 농도·습도는 null 그대로, 사유(`status`)는 글자 그대로 보낸다
  - 성공하면 `sent.txt`를 앞으로 옮긴다. 실패(연결·타임아웃·4xx·5xx)는 종류를 나누지 않고 그대로 두어 다음 실행에 다시 보낸다
- **`estimate.py`** — live 실행 끝에 부른다. **할 일이 없는 실행에서도** 불러야 밀린 행이 다시 나간다. import까지 try 안에 넣어, `send.py`에 문제가 있어도 추정기는 멈추지 않는다. `--latest`(테스트)는 보내지 않는다
- `send.py`가 추정기의 무거운 모듈(cv2)을 불러오지 않도록 모델 이름을 따로 갖고 있다. 그래서 모델을 바꿀 때 `send.py`의 `MODEL`도 같이 바꿔야 한다고 주석과 운영 문서에 적었다

### 머지된 백엔드와 대조

사용자 요청으로 서비스 저장소를 다시 받아 봤다. PR #2 뒤로 새로 머지된 것은 없었고, PR 브랜치는 `main`과 내용이 같았다. 로컬 검증이 머지된 코드 그대로로 한 셈이다.
백엔드가 거절하는 조건(시간대 없는 시각, 정각이 아닌 회차, 문자열 숫자, 숫자 카메라 번호, `pm25_est` 키 누락, 음수, 습도 100 초과)을 하나씩 대조해 모두 맞음을 확인했다.

대조하다 알아둘 것 세 가지가 나왔다.

1. **한 행이라도 틀리면 요청 전체가 거절된다.** 그러면 같은 묶음이 2시간 동안 매분 실패한다. 다만 추정기는 농도를 0 밑으로 안 내리고, 습도는 기상청 값이고, 회차는 늘 정각이라 그런 값을 만들 일이 거의 없다. 고치지 않기로 했다
2. **서비스 문서의 추정 주기가 옛날 것이었다.** `AGENTS.md`와 Notion 가이드에 "5분마다 돌아 두 번에 나뉠 수 있다"고 되어 있었다. 실제로는 10/19부터 1분마다 돈다. 백엔드 코드는 어느 쪽이든 똑같이 받으니 글자만 문제였다.
   - 그런데 프론트 규칙 "`slot`이 바뀌면 다시 그림"과 겹치면 실제 문제가 된다. +5분에 새 회차를 그린 뒤 +6분에 나머지 카메라가 들어와도, `slot`이 같아 다음 회차까지 20분 동안 덜 채워진 지도가 남는다
3. **비 오는 날의 `stale`(값 끊김 경고)이 정해져 있지 않다.** 비 오는 날은 추정기가 null 행을 보내고, 백엔드는 그 회차 격자를 만들지 않는다. 그래서 `/api/frames/latest`가 비 오기 전 지도를 이유 표시 없이 계속 준다.
   - 사용자는 "추정기·전송 문제면 그렇게, 비·습도면 그렇게 실서비스에 알리면 되지 않나"라고 했고, 그게 맞는 해결책이다. 지금 사양(`last_slot`, `stale`만)이 그 구분을 담지 않을 뿐이다
   - 추정기는 이미 행마다 사유를 보내므로 전송 코드 쪽에서 고칠 것은 없다
