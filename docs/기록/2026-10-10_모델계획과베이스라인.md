# 2026-10-10 · 모델 계획과 베이스라인

> 6주차 · 10/8 발표에서 특별한 피드백이 없어 계획대로 모델 단계로 넘어간다.
> 모델을 만드는 순서와 평가 방법, 완성 후의 서비스 형태를 정했고,
> 고농도를 채울 외부 데이터셋을 실제로 받아 확인했다.
> 저녁에는 19일치 사진을 로컬로 받아 첫 베이스라인을 돌렸고, 다 받아진 베이징 데이터를 확인했다.

---

## 요약

- 모델은 **인천 데이터 단독으로 먼저** 만든다. 베이스라인(이미지 통계) → CNN → 기상 결합 순서다
- 평가는 **날짜 단위 분할**로 한다. 외부 데이터는 학습에만 쓰고, 고농도 성능은 따로 떼어 둔 "참고 시험"으로만 본다
- 서비스 형태도 정했다. 수집기와 **분리된 추정기**를 VM에 올리고, **밤에는 측정소 실측값을 IDW로 보간**해 보여 준다.
  "수집할 때마다 학습"은 정답이 1시간 뒤에 나오므로 불가하고, **주기적인 재학습**으로 대신한다
- 에어코리아 약관을 원문으로 확인했다. IDW와 모델 값은 금지 조항에 해당하지 않는다고 보고, **"우리가 계산한 값"으로 표시**하기로 했다
- 외부 데이터 후보 11개 중 실제로 받을 수 있는 건 셋이었다. **베이징을 학습에 쓰기로 했다** — 75 초과 353시간, 매달 맑은 날·탁한 날 공존, 우리 특징이 인천보다 강하게 듣는다.
  허산은 가설 확인용 참고로 두고, 톈진은 받지 않는다
- **첫 베이스라인에서 가설이 일단 성립했다.** 이미지 통계만으로 평균만 찍는 모델 대비 오차를 22% 줄였고, 기상만 쓴 모델(17%)보다 나았다
- 위쪽 1/3 띠 특징만으로도 전체를 다 쓴 것과 점수가 같아 **ROI가 도움이 될 단서**를 얻었다. 약점은 탁한 날을 낮게 맞히는 쏠림이다
- **화각이 바뀐 사진**(관제센터가 돌린 카메라)을 사람이 보고 91장 걸러 냈다. 0.8%만 뺐는데 이미지 모델 오차가 4.91 → 4.67로 줄었다
- 라벨을 다시 만들다 `build_labels.py`의 결함을 찾았다. **API 오류 응답이 정상 자료로 저장돼** 사진 387장이 기상 결측으로 보였다

## 배경

10/8 6주차 발표(피드백 반영, 기상 1분 API 전환, `build_labels.py`)에서는 별다른 피드백이 없었다.
모델 마감(11/11)까지 4주 남짓이라 모델 작업을 시작하기 전에 순서와 형태를 확정해야 했다.
사용자는 AI 모델 담당이지만 모델 설계는 처음이라, 갈림길마다 이유를 듣고 정하는 방식으로 진행했다.

계획을 정한 뒤 바로 1단계(받기 → 라벨 → 거르기 → 베이스라인)에 들어갔다.
현황에 적어 둔 대로 *"이미지 통계가 PM2.5와 실제로 상관이 있는가"*를 수집이 끝나기 전에 확인해 두려는 것이다.
로컬에는 9/21 시험 사진 2장뿐이었고, 사진은 모두 VM에 있었다.

## 한 일

### 모델 만드는 순서

| 단계 | 내용 | 목적 |
|---|---|---|
| 거르기 | 강수(`rain=1`), 고습도(기준은 데이터를 보고 정함), PM2.5 결측, 가려진 화면 | 먼지가 아닌 이유로 흐린 사진 제거 |
| ROI | 하늘·원경 건물만 자른다. 카메라마다 한 번 지정 | 차량·도로 잡음 제거. 산은 단풍 때문에 피한다 |
| 베이스라인 | 대비·채도·암채널·선명도·하늘-원경 밝기차 + 습도·태양고도 → 회귀 | **가설 검증**과 비교 기준선 |
| CNN | 사전학습 백본(ConvNeXt V2-Tiny 등) + 회귀 헤드, 미세조정 | 데이터가 적어 처음부터 학습은 불가 |
| 기상 결합 | 이미지 특징 + 습도·기온·풍속·태양고도 | 같은 흐림이라도 습도가 높으면 먼지 탓이 아닐 수 있다 |

ROI는 처음부터 지정하지 않고 사진 전체로 베이스라인을 먼저 돌려 보기로 했다.
상관이 나오는지부터 보고, ROI는 결과를 본 뒤에 해도 늦지 않다.

CNN에서 짚은 주의점이 하나 있다. 사진 학습에서 흔히 쓰는 **색·밝기 증강은 쓰면 안 된다.**
우리 문제에서는 색과 대비 자체가 정답의 신호라, 그것을 흔들면 정답을 흔드는 셈이다.

### 평가 방법

- **사진을 무작위로 나누지 않는다.** 11:00 사진이 학습에, 11:20 사진이 시험에 들어가면 답을 보고 시험을 치는 셈이다.
  날짜 단위로 나눈다
- 지표는 MAE·RMSE. **늘 평균만 찍는 모델 대비 개선폭**을 반드시 같이 낸다.
  가을이라 농도가 낮은 구간에 몰려 있어 평균만 불러도 MAE가 작게 나올 수 있다
- 정답이 1시간 평균이므로, 같은 시간 사진 3장의 예측을 평균해 비교하는 방식도 같이 본다

### 외부 데이터를 섞는 방식

사용자의 첫 구상은 "인천으로 완성한 모델에 고농도 데이터를 나중에 덧붙여 학습"이었다.
이 순서는 마지막에 본 데이터 쪽으로 쏠려 **인천 장면을 보는 능력이 떨어질 수 있어** 권하지 않았다.

| 방식 | 판단 |
|---|---|
| 인천 → 외부 | 비추천. 인천 성적이 나빠질 수 있다 |
| 외부 → 인천 | 가장 흔한 방식. 인천은 안정적이나 고농도 감각이 흐려질 수 있다 |
| 섞어서 한 번에 | 둘 다 유지하기 좋으나 비율을 맞춰야 한다 |

뒤의 둘 중 무엇이 나은지는 **둘 다 해 보고 숫자로 고른다.** 시험지는 둘이다.

- **A. 인천 시험** — 인천 데이터 중 학습에 안 쓴 날짜. 모든 실험에서 같은 시험지. 본 성적이다
- **B. 고농도 참고 시험** — 외부 데이터 중 학습에 안 쓴 날짜

함정도 하나 정리했다. 외부에 고농도만 있고 인천에 저농도만 있으면, 모델이 흐림이 아니라
**"베이징 건물이면 높다, 인천 건물이면 낮다"를 외울 수 있다.**
그래서 외부 데이터도 같은 카메라 안에 맑은 날과 탁한 날이 함께 있어야 한다.

외부 데이터를 결국 못 구해도 인천 단독 결과만으로 결과물은 완성된다. 그때는 "0~35 범위에서 검증"을 한계로 밝힌다.

### 서비스 형태 — 무엇이 되고 무엇이 안 되나

사용자가 그린 최종 형태는 이렇다. VM에서 20분마다 수집하고 추정해 백엔드로 보내고,
가능하면 수집할 때마다 학습하고, 백엔드 DB에 쌓아 타임라인으로 과거를 넘겨 볼 수 있게 한다.

| 구상 | 판정 | 이유 |
|---|---|---|
| 20분마다 추정해 백엔드로 전송 | 가능 | 형식은 9/22에 정한 `values.json` 그대로 |
| DB에 쌓아 타임라인으로 보기 | 가능 | 숫자 20개 × 하루 30여 회차라 작다 |
| **수집할 때마다 학습** | **불가** | 11:20 사진의 정답(12:00 값)은 12:15쯤 게시된다. 찍는 순간에는 학습할 짝이 없다 |
| 주기적 재학습 | 가능 | 쌓인 데이터로 로컬 GPU에서 학습 → **시험 점수가 나을 때만** VM 모델 교체. 주 1회 정도 |
| VM에서 CNN 추정 | 미확인 | e2-micro 메모리 1GB. ONNX로 가볍게 하거나 VM 사양을 올려야 할 수 있다 |

정답이 늦게 온다는 점은 오히려 기능이 된다. 타임라인에 **그때의 추정값과 나중에 확정된 실측값을 나란히** 보여 줄 수 있다.

추정기는 **수집기와 별도 프로그램**으로 둔다. 수집기 안에 넣으면 추정 쪽 오류로 수집이 멈출 수 있고,
이미지는 놓치면 영구 손실이다. `build_labels.py`를 분리한 것과 같은 원칙이다.

**밤 처리는 사용자가 제안했다.** 밤에는 사진을 안 찍으므로 추정이 불가하니, 측정소 실측값을 IDW로 보간해
빈 격자 없이 보여 준다. 받아들이면서 붙인 조건은 이렇다.

- 낮(CCTV 추정)과 밤(측정소 실측 보간)을 화면에서 구분한다
- 밤 값은 1시간 평균에 15분 늦게 게시되므로 **몇 시 기준인지** 같이 표시한다
- 경계 지역은 경기도 도시대기 측정소도 넣는다
- 밤에 실측 IDW를 보여 주면 "그럼 낮에도 IDW면 되지 않나"는 질문이 나온다.
  인천은 측정소가 촘촘해 공간 이득이 작을 수 있으므로 **"20분 간격, 더 빨리"를 앞세운다**

### 1단계 ① 사진을 로컬로 받기

받는 방법은 셋을 놓고 골랐다. 브라우저 SSH 창에서 직접 내려받기, 로컬에 gcloud 설치, 일부(매시 :20)만 먼저 받기.
**gcloud를 골랐다.** 주 1회 재학습을 하려면 받기를 계속 반복해야 하는데, 브라우저 방식은 매번 손으로 해야 한다.

처음에는 `gcloud compute scp`를 썼는데, 윈도우에서는 PuTTY(pscp)로 돌아 초당 0.3MB밖에 나오지 않았다.
같은 키로 OpenSSH `scp`를 4개 동시에 돌리자 초당 약 3MB가 나와 2.9GB를 20분 만에 받았다.
VM에서 날짜별로 tar로 묶어 보냈고(파일 1만 개를 하나씩 보내는 것보다 빠르다), 받은 뒤 체크섬과 장수를 대조했다.
절차는 `운영.md` §3에 옮겨 두었다.

전송 요금은 받고 난 뒤에야 확인했다. VM의 무료 아웃바운드는 월 1GB라 이번 분량은 소액(약 $0.2~0.3으로 추정)이 붙는다.
받기 전에 알렸어야 했다.

### 1단계 ② 라벨 다시 만들기 — 저장된 오류 응답

`build_labels.py`는 기상 1분값을 관측소·날짜마다 하나씩 받는다. 새로 생긴 12일치(파일 77개)에 **약 45분**이 걸렸다.
응답이 중간에 끊겨 다시 받는 일이 잦았고, 네 번 연속 끊겨 스크립트가 멈춘 것도 두 번이었다. 받은 것은 저장되므로 다시 돌려 이어 갔다.

결과에서 기상 빈칸이 387장 나왔다. 첫 실행(9/22~28)에서는 0이었다.
원인을 찾아보니 112번 관측소의 10/1·10/2, 511번의 10/2 저장본에 **자료 대신 오류 문구 한 줄**만 들어 있었다.
오류 응답에도 끝 표시가 붙어 있어 10/1에 넣어 둔 "끊긴 응답 거르기"를 통과했고, 저장본이 있으니 다시 받지 않았다.
같은 날을 다시 요청하자 1,440분이 다 왔다 — 일시적인 오류였다.

그대로 두면 그날들은 **영구 결측으로 보이게** 된다. 9/22에 수집기에서 없앤 "결측이 드러나지 않는 경로"와 같은 성격이라,
자료 줄이 없으면 다시 받고, 그래도 없으면 저장하지 않고 경고하도록 고쳤다. 다시 돌리자 빈칸은 2장(실제 결측)이 됐다.

로그를 날짜별로 세다가 **9/27에 카메라 18대가 07시대부터 하루 종일 실패**한 것도 발견했다(성공 107장).
실패한 카메라와 성공한 카메라가 같이 있어 우리 쪽보다는 스트림 서버 쪽 문제로 보이지만 원인은 확인하지 않았다.

### 1단계 ③ 무엇을 잴 것인가

계획은 "처음엔 사진 전체로"였다. 20대를 한 장에 모아 보니 **아래쪽은 도로·차량·자막이고, 하늘과 원경 건물은 거의 다 위쪽 1/3**에 있었다.
그래서 같은 통계를 사진 전체와 위쪽 1/3 띠에서 각각 잰다. 카메라마다 영역을 지정하는 ROI가 아니라 일률적으로 자른 띠라,
"ROI는 결과를 보고 정한다"는 순서는 그대로다.

특징은 밝기·대비·채도·암채널·선명도·파랑/빨강 비, 위−가운데 밝기차다. 해상도가 세 가지(640×360·960×540·1280×720)라
선명도가 해상도를 따라가지 않도록 모두 640×360으로 줄인 뒤 잰다.

### 1단계 ④ 시험지를 어떻게 떼어 둘까

시험 A는 "모든 실험에서 같아야" 하는데 데이터가 계속 늘어난다. 세 안을 놓고 사용자가 골랐다.

| 안 | 판단 |
|---|---|
| **고정 규칙 날짜 + 나머지로 교차검증** | 채택. 9/22부터 센 날짜 번호를 4로 나눈 나머지가 3인 날. 새 날짜도 같은 규칙이라 시험지가 흔들리지 않고, 날씨 국면이 고루 섞인다 |
| 마지막 며칠 | 실제 서비스 상황과 같지만, 그 며칠의 날씨에 점수가 좌우되고 데이터가 늘면 시험지가 바뀐다 |
| 교차검증만 | 데이터를 가장 많이 쓰지만, 모델을 고르는 데 쓴 점수가 곧 최종 점수가 되어 부풀려진다 |

지금 날짜 중 시험 A는 9/25·9/29·10/3·10/7이고, **아직 열지 않았다.** 개발 점수는 나머지 14일로 하루씩 빼고 학습해서 낸다.

### 1단계 ⑤ 무엇과 비교해야 "신호가 있다"고 말할 수 있나

평균만 찍는 모델 하나로는 부족했다. 두 가지 비교를 더 넣었다.

- **카메라별 평균**: 모든 모델에 카메라 번호가 들어가므로, 측정소마다 평소 농도가 다른 것만으로도 점수가 오른다. 그것보다 나아야 한다
- **기상만**: 습도가 높은 날 PM2.5도 높은 경향이 있어 사진 없이도 어느 정도 맞는다. 이미지가 이것을 넘어야 "사진에 정보가 있다"고 말할 수 있다

습도는 PM2.5 구간을 고정하고 습도별로 암채널을 나눠 봤다.

| | PM 0~10 | 10~15 | 15~20 | 20~30 | 30~ |
|---|---|---|---|---|---|
| 습도 ~60% | −0.43 | −0.11 | 0.13 | 0.23 | 0.34 |
| 70~80% | 0.10 | 0.49 | 0.45 | 0.85 | 1.13 |
| 95%~ | 0.49 | 0.82 | 1.12 | 1.71 | 2.61 |

(위쪽 띠 암채널, 카메라마다 표준화한 값의 평균)

가로로 읽으면 같은 습도에서도 PM2.5가 높을수록 대체로 커지고, 세로로 읽으면 같은 PM2.5에서도 습도가 높을수록 커진다.
**먼지 신호가 습도와 따로 있고, 습도도 같은 방향으로 흐리게 만든다**는 뜻이다(후자는 흡습 성장으로 추정).
습도 효과가 어느 지점에서 꺾이지 않아, 습도 기준은 90%·95%·없음을 점수로 비교했다. 차이가 0.01 이내라 안개 위험을 줄이는 95%로 정했다.

### 1단계 ⑥ 결과

거르기 후 10,603장, 18일(PM2.5 0~48, 평균 12.7). 개발 14일 교차검증 MAE:

| 모델 (Ridge) | MAE | 평균만 대비 |
|---|---|---|
| 평균만 | 6.30 | — |
| 카메라별 평균 | 6.16 | +2% |
| 기상만 | 5.24 | +17% |
| 이미지만 | 4.91 | +22% |
| 이미지+기상 | 4.81~5.05 | +20~24% |

- 이미지만으로 기상만보다 낫다. **가설은 일단 성립한다**
- 특징 범위를 바꿔 보면 위쪽 띠만 4.86, 사진 전체만 5.12. **위쪽에 신호가 몰려 있다** — ROI 단계의 근거
- 비선형인 부스팅 모델은 4.69로 조금 낫다. 정식 비교는 CNN과 같이 하기로 했다
- **예측이 평균 쪽으로 쏠린다.** 가장 탁했던 10/9(평균 25)를 약 10 낮게 맞혔다. 예측-정답 상관 r=0.51.
  고농도 데이터가 적은 것(§5 구조적 리스크)과 같은 방향의 문제로 보이지만 원인은 아직 보지 않았다

### 두 세션이 같은 파일을 만들었다

1단계 진행이 오래 걸리자, 사용자가 대화를 fork해 다른 세션에서 코드 작업을 진행했다.
두 세션이 각자 `Model/features.py`와 `Model/baseline.py`를 만들었고, **이 세션이 fork 쪽 파일을 덮어썼다.**
파일을 쓸 때 "새로 만듦"이 아니라 "갱신됨"이 나왔는데 확인하지 않았다. fork는 바뀐 것을 알아채고 되돌리지 않은 채 사용자에게 알렸다.

정리는 두 버전을 비교해 정했다. 특징 추출은 위쪽 띠 효과가 숫자로 확인된 이 세션 것을 쓰고, fork의 아이디어 둘을 받아들였다.

- **카메라 차이를 다루는 방식을 여럿 남기기.** 처음에 "카메라별 표준화와 카메라 번호를 합치면 둘의 약점을 다 막는다"고 했는데,
  같은 조건으로 돌려 보니 근거가 없었다(아래 정정). 사용자가 "베이스라인이라 큰 의미는 없으니 셋 다 남기자"고 해서 성적표에 나란히 둔다
- **사진별 예측값 저장.** 평균 오차만으로는 어디서 틀리는지 알 수 없다. 탁한 날 쏠림을 들여다볼 재료다

fork의 **규제 세기 자동 선택은 넣지 않았다.** 0.01~10에서 점수가 같았다. 학습 8천 장에 특징 40개 미만이라 과적합 여지가 작다.
fork 때는 6일치라 이 값이 중요했다. fork가 README에서 고친 깨진 경로 4곳(`\b`·`\a`·`\r` 제어문자)은 그대로 살렸다.

### 외부 데이터 확인 — 허산과 베이징

베이징 다운로드가 끝나 두 데이터를 우리 특징 추출(`Model/features.py`의 계산)로 직접 재 봤다.
"쓸 만한가"의 기준은 셋이다. 고농도가 충분한가, 같은 카메라 안에 맑은 날과 탁한 날이 같이 있는가, 우리 특징이 듣는가.

**허산 — 재는 곳에 따라 신호가 생기고 사라졌다.** 처음 돌린 위쪽 1/3 띠 특징은 세 방향 모두 상관이 거의 없었고,
위쪽 띠 선명도는 오히려 반대 방향(+0.26)이었다. 사진을 늘어놓고 보니 허산은 **화면의 80%가 하늘**이고
먼 산은 맨 아래 15~20%에만 있었다. 인천 CCTV에서 "위쪽 = 하늘·원경"이던 띠가 허산에서는 하늘만 잰 것이다.
지평선 아래 원경 띠로 바꾸자 세 방향 모두 대비 −0.30~−0.35, 암채널 +0.12~+0.34로 예상 방향이 나왔다.
노을이 끼는 오후를 빼면 암채널이 +0.37~+0.47로 더 강했다.
폰으로 손에 들고 찍어 구도가 매번 조금씩 다르고 라벨이 반나절 단위라, 오전 판단대로 학습에는 쓰지 않고 **35~100 구간 가설 확인용**으로 둔다.

**베이징 — 학습에 쓰기로 했다.**

| 기준 | 결과 |
|---|---|
| 고농도 | 낮 3,150시간 중 75 초과 353시간(66일), 150 초과 101시간(17일). 최고 262 |
| 맑은 날·탁한 날 공존 | 매달 15 미만과 75 초과가 같이 있다(5·8·3월은 75 초과가 적다) |
| 특징이 듣는가 | 암채널 +0.55, 채도 −0.53, 위쪽 띠 대비 −0.53. **달마다 따로 봐도 같은 방향**(암채널 +0.20~+0.59) |

달마다 따로 본 것은 **계절 함정** 때문이다. 베이징은 겨울에 탁하고 같은 때 나무가 앙상해진다.
전체로만 상관을 보면 "나무 색"을 보고 맞힌 것인지 구분이 안 된다. 같은 달 안에서도 같은 방향이 나오므로 나뭇잎 때문만은 아니다.

라벨 시각도 확인했다. 엑셀에는 저자가 사진에서 잰 평균 RGB가 있어, 같은 값을 우리가 재서 대조했다.
`Time` H 행은 **H:00~H:59 사진 2장의 평균**과 일치했다(상관 0.9988, 한 시간 앞 사진과는 0.87).
저자는 그 시간 사진에 같은 행의 PM2.5를 붙인 것이다. 그런데 사진 특징은 13개 모두 **한 시간 뒤 행의 PM2.5와 조금 더 잘 맞았다**(차이 0.01~0.03).
PM2.5가 에어코리아처럼 끝 시각 표기일 수 있다는 뜻이지만, 차이가 작아 **미확인으로 두고** 학습 전에 정하기로 했다.

걸리는 점도 있다.
- **지상 습도가 없다.** 상공 습도(500·700·850hPa)와 2m 기온, 강수, 경계층 높이만 있다. 인천의 습도 거르기와 기상 결합을 그대로 쓸 수 없다
- 원경이 짧다. 화면 대부분이 가까운 나무와 건물이고 먼 탑 하나가 보인다
- 사진이 90° 누워 있다. 돌려서 쓴다
- 저장소에 라이선스 표기가 없다. 논문 인용으로 쓰고 재배포하지 않는다

베이징으로 고농도가 충분해 **톈진(5.6GB)은 받지 않았다.**

**베이징 두 문제 정리.** 학습에 섞기 전에 정할 것이 둘이었다.

*① 정답을 어느 행에서 가져올까.* 중국 생태환경부 표준 HJ 633-2012를 원문으로 확인했다.
§5.1.2는 일보 구간을 "당일 0시 이전 24시간"으로, §5.1.3은 실시간 보고를 "1시간 주기, 매 정시가 지난 뒤 발표"로 정한다.
끝나는 시각으로 부르는 표기로 읽히지만 1시간 값에 "앞 1시간"이라고 쓴 문장은 아니어서 사진으로도 확인했다.
정답 행을 −1~+3시간 밀어 가며 보면 농도 수준끼리는 +1·+2시간이 비슷했다. 농도는 몇 시간씩 이어지므로 이것으로는 못 가른다.
**한 시간 동안의 변화량끼리** 보면 +1시간이 뚜렷하게 높았다(암채널 0.04 / 0.13 / 0.08).
표준과 사진이 같은 쪽을 가리켜 **H시대 사진에 H+1 행**을 붙이기로 했다. 저자의 짝짓기(같은 행)와는 한 시간 다르다.

*② 습도.* 처음 후보는 ERA5였다. Open-Meteo에서 ERA5만 지정해 받으니 엑셀 기온과 같은 격자였다(상관 0.9986, 차이 중앙값 0.38℃).
그런데 베이징 관측소 54511(ISD 표기 수도공항)의 실제 관측(NOAA ISD)과 비교하자 ERA5가 **높은 습도를 낮게 말했다** — 관측 94%일 때 ERA5 87%,
관측 95% 이상 96시간 중 50시간만 잡았다. 습도의 첫 용도가 95% 이상 거르기라 관측값 쪽을 추천했지만, **출처는 확정하지 않았다.**
사용자가 "ERA5면 30분마다 찍은 사진에 정확한 습도를 붙일 수 있나"를 물었는데, **ERA5도 정시 값뿐이라 안 된다**(받은 자료가 290일 × 24시간 = 6,960행).
두 출처 모두 1시간 간격이라 정시 값을 30분 간격 사진에 어떻게 붙일지는 어느 쪽이든 정해야 한다.
앞뒤 정시 사이 보간을 추천했고, 사용자가 출처와 시각 맞추기를 함께 더 생각해 보기로 했다.

카메라 위치를 알려고 논문 원문을 찾았다. 출판사가 자동 접근을 막았고 Google Scholar에도 무료 공개본은 없었다.
학교 도서관의 KERIS ScienceDirect 수록 목록(2022년 1월 기준)에 Atmospheric Environment가 2005년부터 들어 있어,
RISS 소속기관 인증을 신청해 두었다(승인 대기). 대신 저자 저장소의 ERA5 추출 노트북에서 **"奥体中心", 39.98°N 116.40°E**를 찾았다.
베이징 국가 대기 측정소 이름과 같아 카메라도 그 근처일 것으로 추정하고, 그렇다면 54511까지 약 19km다.

결국 사용자가 **관측소 54511로 정했다.** 습도를 빼면 인천과 입력이 달라지고, ERA5는 안개 거르기에 쓸 수 없기 때문이다.
"엑셀에 있던 공중 습도로는 안 되나"도 확인했다. 낮 시간 지상 습도와의 상관이 850hPa 0.55, 700hPa 0.42, 500hPa 0.32였고,
지상 95% 이상인 시간에 850hPa도 95% 이상인 경우는 29%뿐이었다. PM2.5와의 상관도 지상 0.50, 850hPa 0.20으로 차이가 컸다.
사진이 보는 것은 지면 가까운 공기라 상공 습도로는 대신할 수 없다.

마지막으로 정시 값을 사진 시각에 맞추는 방식을 정했다. 사용자는 처음에 "30분마다 찍었으니 시각이 맞지 않나"라고 물었는데,
실제 간격은 약 30분 26초라 촬영 분이 매번 밀려 한 시간 안에 고르게 퍼져 있었다(정확히 :00분은 2%).
세 방식의 오차를 **인천 1분 자료로 실험했다.** 정시 값만 남기고 그 사이 분을 추정해 실제 1분 값과 비교한 것이다.
보간은 오차 중앙값 1.05%p, 정시 ±10분 사진만 쓰면 0.80%p지만 베이징 사진의 3분의 2를 버리고, 같은 시간대 정시 값은 2.10%p에 22%가 5%p 넘게 틀렸다.
**보간으로 정했다.** "앞뒤 차이가 크면 결측" 안전장치도 재 봤지만 최대 오차(15%p)가 그대로여서 넣지 않았다 —
크게 틀리는 순간은 정시 사이에 잠깐 튀었다 돌아오는 경우라 앞뒤 정시 값으로는 잡히지 않는다.
시각이 정확히 같은 값만 쓰는 §2 원칙의 예외이므로 이유를 현황에 같이 적었다.

### 1단계 ⑦ 화각 변경·깨진 화면 거르기

계획의 마지막 거르기 항목이 "가려진 화면"이었다. 무엇이 실제로 있는지부터 찾았다.
사진마다 ①카메라 평소 모습과 닮은 정도, ②20분 전 사진과의 차이, ③화면이 한 가지 색인지를 재고 가장 이상한 사진부터 늘어놓았다.
차나 물방울에 가려진 사진은 없었다(비 오는 날은 이미 강수로 빠짐). 대신 둘이 나왔다.

- **깨진 화면** — 10042번 10/8 아침 6장. 회색 화면 5장은 20분 전 사진과 완전히 같았다
- **화각이 바뀐 사진** — 생각보다 흔했다. 79·17·113·134·13·103·112·62번이 몇십 분~몇 시간 다른 곳을 비췄다가 돌아왔다.
  관제센터가 카메라를 돌린 것으로 보인다. 121번은 10/9 하루 종일 다른 화각이었다

처음 기준은 "위쪽 윤곽선이 평소와 닮았나"였는데, 경계 근처 사진을 늘어놓자 **대부분 화각은 정상이고 뿌연 사진**이었다.
먼지와 연무가 먼 건물의 윤곽을 지우니 뿌연 사진이 화각 변경처럼 보인 것이다. 이 기준으로 걸리는 727장의 PM2.5 평균은 16.2로
나머지(12.6)보다 높았다. 그대로 썼다면 지금도 모자란 탁한 날 사진을 우리 손으로 버렸을 것이다.

그래서 **특징점이 평소 자리에 있는지**로 바꿨다. 화각이 바뀌면 물체가 옮겨 가지만 뿌옇게 되면 위치는 그대로다.
기준 사진과 ORB 특징점을 맞춰 화면 이동량(픽셀)을 구했고, 이 값은 카메라 안에서 PM2.5와 상관이 없었다(중앙값 −0.02).
사진으로 보니 10~20픽셀은 같은 장면이 조금 흔들린 경우가 많고 60픽셀 넘게는 거의 다 다른 화각이었다. 그 사이는 섞여 있었다.

기준을 숫자로 정하는 대신 **사용자가 직접 보고 판단하기로 했다.** 이동량 10픽셀 초과와 깨진 화면 193장을 카메라별로 평소 모습 옆에 늘어놓는
검토 페이지를 만들었다(번호판이 찍힐 수 있어 웹에 올리지 않고 `data/` 아래 파일로). 사용자는 91장을 제외했다.
기본값(20픽셀 초과 제외)에서 24장을 바꿨는데, 124번의 두 번째 고정 위치 14장은 같은 장면으로 보고 남겼고 121번 10/9는 20장 전부 뺐다.

이 절차를 `Model/view_check.py`로 만들었다. 검토 결과(`Model/view_review.csv`)와 카메라별 기준 사진(`Model/view_ref.csv`)은
사진 경로와 결정뿐이라 저장소에 올린다. 새 사진은 같은 페이지로 검토하고, 검토 전에는 기본 기준으로 거른다.

**결과: 90장(0.8%)만 뺐는데 이미지 모델 오차가 4.91에서 4.67로 줄었다**(평균만 대비 22% → 25%). 사진을 안 쓰는 기상만은 5.24 → 5.20으로 거의 그대로다.
화각이 바뀐 사진이 "평소 모습 대비 얼마나 뿌연가"를 재는 특징을 흐리고 있었다는 뜻이다.

### 사진 전수 검수와 베이징 라벨 표

사용자가 10/15 발표 목표를 밝혔다. **10/9까지의 인천 데이터와 베이징으로 학습한 모델의 성능평가**다.
발표용 학습 데이터는 오점이 없기를 원해서, 자동 거르기는 그대로 두고 **사진 전체를 직접 넘겨보기로** 했다.
나는 표본 검사나 카메라·날짜별 모아보기로 충분하다고 권했지만(정답 자체의 흔들림이 더 크고, 치우치지 않은 오류는 모델이 흡수한다),
사용자에게는 넘겨보는 방식이 편했다. 인천 11,420장을 카메라별 폴더에 촬영 순서대로 복사했다(`incheon_review\`, 폴더당 385~596장).
검수 결과로 자동 기준을 나중에 조정한다.

이어서 베이징을 인천 `labels.csv`와 **같은 13칸**으로 만들었다(`Tools/build_labels_beijing.py`).
- 사진: 베이스라인 특징은 인천을 640×360으로 줄여 재는데, 인천 원본은 모두 16:9라 찌그러지지 않는다. 돌린 베이징은 9:16이라 같은 크기로 만들면 찌그러진다.
  그래서 **비율은 지키고 화소 수를 맞추는** 쪽으로, 똑바로 돌려 540×960으로 저장했다
- `image` 칸을 사진 폴더 기준 상대 경로(`bj/날짜/HHMM.jpg`)로 둬서, 검수 후 `data\images\`로 옮겨도 표를 다시 만들 필요가 없다
- 비: 엑셀에는 ERA5 강수량뿐이라 54511의 **현재 날씨 코드**(WMO 4677)를 썼다. 50~99를 비로 본다.
  코드와 ERA5를 대조하니 비 코드 시간에 ERA5도 강수가 있는 비율이 70%, 맑은 코드에서는 1~3%여서 해석이 맞았다. 소나기·뇌우는 ERA5가 절반을 놓쳤다
- 그러다 **54511이 30분마다 관측한다는 것**을 알았다. 처음에 정시 값만 남겨 1시간 간격으로 잘못 봤다. 다시 재니 보간 오차가 더 작았다(아래 정정)

결과는 낮 사진 6,483장, PM2.5 75 초과 663장·150 초과 198장, 비 감지 304장이다. 검수용 사본은 `beijing_review\`에 한 폴더로 두었다.

## 남은 문제

- **탁한 날 쏠림 분석.** `data/model/baseline_pred.csv`로 10/9를 모든 카메라가 낮게 맞혔는지, 특정 카메라·시간대만 그런지 본다
- ROI 지정 → CNN(ConvNeXt V2-Tiny). 기준점은 이번 베이스라인(화각 거르기 후 MAE 약 4.7)
- **베이징 사진 검수**: `beijing_review\`를 사용자가 넘겨보며 이상한 사진을 고른다. 끝나면 `bj` 폴더를 `data\images\`로 옮긴다
- **베이징 논문 원문**: RISS 소속기관 인증 승인 대기. 받으면 카메라 위치·PM2.5 측정소를 확인한다
- 베이징 카메라 정확한 위치 (관측소 54511과의 거리)
- 백엔드 조원과 정할 것: 추정값 전송 방식, 백엔드·DB를 어디서 돌릴지(e2-micro에 다 올리면 메모리 부족), 저장 항목(나중에 채울 실측값 칸 포함), 밤 화면 표시
- VM에서 CNN 추정이 메모리에 들어가는지는 모델이 나온 뒤 실측한다
- 3개월 상한 조항이 1월 재학습(9~10월 라벨 사용)에도 걸릴 소지가 있다. 포트폴리오 목적이라 크게 보지 않기로 했다
- 수집기 알림 문구("복구 불가")는 그대로다
