# 2026-10-15 · 서비스 모델 교체

> 7주차 · 인천+베이징 ver도 인천 고농도를 못 맞힌다는 점을 사용자가 짚어, 발표 3시간 전에 서버 추정기를 인천 ver로 바꿨다.
> 발표 자료의 서비스 모델 부분(14·21·22번)과 노션 대본도 같이 고쳐 7주차 발표를 했다.

---

## 요약

- 사용자 질문: "인천+베이징 ver도 인천 고농도를 못 맞히는데, 볼 일도 없는 베이징 사진을 배운 모델을 서비스에 쓸 근거가 있나?" — 확인해 보니 **근거가 약했다**
- 인천 '나쁨'(36~75) 94장에서 인천 ver 오차 **17.4**, 인천+베이징 ver **19.0**. 실제 평균 39.7을 각각 22.3·20.7로 불렀고, 둘 다 36을 넘긴 예측이 없었다
- 인천 숫자는 모두 인천 ver가 같거나 낫다(교차검증 3.37 대 3.54, 테스트 A 2.46 대 2.48). **추정기를 인천 ver로 교체**했고 10/15 11:25 회차부터 새 모델이다(19장 정상, 오류 0)
- 습도는 모델 입력에서만 빠지고 **비·습도 95% 거르기 때문에 계속 조회**한다
- 덱 14·21·22번과 노션 대본을 새 서비스 모델에 맞춰 고쳤다. 인천+베이징 ver는 버리지 않고 인천 고농도 날이 쌓이면 다시 비교할 후보로 둔다

## 배경

10/13 밤 추정기를 올릴 때 서버에는 인천+베이징 ver(`mixed_top60_w-hum`, ⑤ + 습도)를 올렸다.
10/14 밤 덱 14번에는 그 이유를 "인천 오차는 사실상 같고 고농도까지 대비"로 적었다. 이 문구는 Claude가 쓴 것이었다.
그런데 덱의 한계 슬라이드(18번)는 "인천+베이징 ver도 인천 '나쁨'을 하나도 못 맞혔다"였다. 사용자가 이 둘이 맞지 않는다고 짚었다.

## 한 일

### 인천 '나쁨'을 얼마나 못 맞혔나

교차검증 예측(사진마다 그 날을 본 적 없는 모델이 낸 값)으로 계산했다.

| | 인천 ver | 인천+베이징 ver |
|---|---|---|
| 실제 평균 | 39.7 | 39.7 |
| 예측 평균 | 22.3 | 20.7 |
| 평균 오차 | **17.4** | **19.0** |
| 가장 높게 부른 값 | 28.7 | 29.6 |

- 두 모델 모두 실제의 절반쯤으로 불렀다. 베이징 고농도를 배운 효과가 인천에서는 나타나지 않았고, 인천+베이징 ver가 오히려 1.6 더 낮게 불렀다
- 가장 탁했던 10/9(69장)도 실제 40을 22로 불렀다(인천+베이징 ver)

### 서비스 모델을 다시 따짐

| | 인천 ver | 인천+베이징 ver (당시 서버) |
|---|---|---|
| 인천 교차검증 | **3.37** | 3.54 |
| 인천 테스트 A | **2.46** | 2.48 |
| 인천 '나쁨' 94장 | **17.4** | 19.0 |
| 베이징 PM 190 사진 | 20 | 182 |

- 인천+베이징 ver의 장점은 "베이징 수준의 고농도"뿐인데, 그것이 인천 카메라에서 통한다는 증거는 없다(인천 '나쁨'에서 이미 효과가 없었음)
- 사용자는 "습도를 넣으면 인천 교차검증에서 손해였으니 해가 되는 모델을 올려 둔 셈"이라고 했다. 크기를 나눠 보면 이렇다.
  - 습도 효과만(같은 인천+베이징 ver끼리): 교차검증 3.45 → 3.54(+0.09), 테스트 A 2.52 → 2.48(−0.04). 같은 설정 재실행 흔들림(0.03~0.04)을 생각하면 인천에서는 득도 실도 거의 없다
  - 인천 ver와의 차이(교차검증 0.17)는 흔들림보다 분명히 크다. 실수가 아니라 10/13 고르는 규칙("인천은 최고와 0.1 이내 손해까지 허용하고 베이징을 올린다")이 원래 그렇게 설계된 결과다
- 그래서 덱 14번의 "인천 오차는 같고 고농도까지 대비"는 과장이었다. 정확히는 "고농도 대비는 베이징에서만 확인했고 인천에서는 아직 확인되지 않음"이다
- 두 모델을 추정기에서 같이 돌려 둘 다 기록하는 방법도 이야기했지만(VM 메모리 상한 600MB 확인 필요) 이번에는 하지 않았다

### 추정기 교체

Claude는 "발표 직전에 운영 서버를 건드리는 위험"을 들어 발표 뒤 교체를 권했다. 사용자는 "발표까지 3시간 남았다, 교체부터"라고 정했다.

- Claude가 처음에 "인천 ver는 기상을 안 쓰니 습도 조회도 필요 없어진다"고 했는데 틀렸다. 습도는 ① 모델 입력과 ② 비·습도 95% 이상 거르기 두 곳에 쓰이고, ②는 학습에서도 뺀 조건이라 모델과 상관없이 필요하다. 거르기는 이미 모델 실행 전에 따로 하고 있어서, 모델 `.json`에 기상 칸이 있을 때만 습도를 입력으로 넣도록 한 곳만 고쳤다
- `incheon_log_top60`을 ONNX로 바꿨다(112MB, PyTorch와 최대 차이 0.00002 ㎍/㎥)
- PC에서 `--latest`는 PC에 최근 수집 기록이 없어 돌지 않았다. 대신 저장된 테스트 사진 몇 장을 추정기 경로로 돌려 학습 코드의 예측과 비교했다(차이 0.15 이내)
- **모델 파일을 먼저 VM에 올리고(체크섬 확인) 그다음 코드를 받았다.** 순서가 반대면 그 사이 회차가 없는 모델 파일을 찾다 실패한다. 추정기는 5분마다 새로 뜨는 방식이라 재시작은 필요 없었다. 수집기는 건드리지 않았다
- 11:25:22 회차부터 새 모델: 19장 모두 정상, 79.4초, 오류 0. 결과 페이지에도 `모델 incheon_log_top60`으로 나온다
- 10/14 하루 대조(MAE 2.17)는 바꾸기 전 인천+베이징 ver로 낸 결과다. 어느 모델의 값인지는 `estimated_at`이 교체 시각 전인지 후인지로 가른다

### 발표 자료와 대본

- **14번**: "서비스 모델" 표시를 인천 ver로 옮기고, 이유를 "인천에서 가장 정확 · 베이징 학습 효과는 인천 고농도에서 아직 미확인"으로 바꿨다(그래프 `c03`·`c02` 다시 그림)
- **21번**: "모델 = 인천 ver", 습도는 거르기에만 쓴다는 한 줄. 결과 페이지 화면을 새 모델 값으로 다시 찍었다
- **22번**: 하루 대조가 교체 전 인천+베이징 ver의 결과라는 표시
- **노션 대본**: 그사이 사용자가 직접 고친 1·2·3·11·12·13번은 건드리지 않고 14·21·22번만 바꿨다. pptx 발표자 노트에는 사용자가 노션에서 고친 부분이 반영되지 않았다(노션을 보며 발표)
- 11:55에 내보낸 최종 pptx에서 14·21·22번 노트가 지시문과 같은 것을 확인했다

이어서 오후에 7주차 발표를 했다. 발표 피드백은 이 기록에 들어 있지 않다.
