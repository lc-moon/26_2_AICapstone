### DB 테스트 — 처음 보고가 틀렸다

- PR 설명은 "DB 테스트 30개 건너뜀(로컬 DB 접속 불가)"이었다. Claude는 처음에 "아무도 안 돌렸다, 팀장 PC의 PostgreSQL은 비밀번호를 몰라 못 돌린다"고 보고했다
- 사용자가 "DB가 있는데 왜 테스트를 못 해 봤나, 원래 어떻게 했었나"를 물었다. 실제 서비스 DB는 테스트가 표를 지우므로(`DROP SCHEMA`) 쓰면 안 되고, 이름이 `_test`인 DB가 따로 필요하다.
  PR #5 때는 **임시 PostgreSQL**을 띄워 돌렸다(PR 설명). 이번에도 이 PC의 PostgreSQL 18로 임시 DB(빈 폴더에 `initdb`, 비밀번호 없음, 다른 포트)를 띄워 PR 코드를 돌렸고 **109개 통과**(DB 30개 포함), 임시 DB는 지웠다
- "서비스에 DB가 정말 필요한가"도 물었다: 배포 서버에 PostgreSQL 16이 있고 지도·측정소·추정값이 모두 DB에서 나온다. "나중에 예측할 때 쓰려고"가 아니라 지금 쓰고 있다

  지난 PR들처럼 한국어 제목·본문 불릿으로 스쿼시 머지했다(`e143e5e`)

- 사용자가 `git pull` + 재시작. 명령 끝의 health가 비어 보였는데 재시작 직후라 응답 전이었던 것으로 보이고, 곧 정상으로 응답했다.

### 측정소 값의 남은 걱정 두 가지

- **오래된 값**: 측정소 값은 에어코리아 수집이 멈출 때(키 만료·API 장애)만 오래된다. 화면에 측정 시각이 같이 나오고, 사용자는 멈출 일이 거의 없다고 봐서 그대로 두었다
- **빈 값의 이유**: `airkorea.py`는 "-"를 `null`로 두고 이유(`pm25Flag`, 예: "점검및교정")를 `pm25_flag`에 따로 저장한다. 화면엔 "값 없음"만 나온다.
  이유를 응답에 더해 보여 주는 것은 mock(팀장)·화면(금혁)이 걸려 있어 **조원 작업이 끝난 뒤 팀장과 같이** 하기로 미뤘다

### 조원 작업은 브랜치가 아니라 담당 폴더로 판단

- 사용자는 "브랜치가 있으면 작업 중이니 건드리지 말고, 없으면 건드려도 된다"로 이해하고 있었다.
  그런데 PR #8은 커밋 21:43, PR 21:45로, GitHub에 브랜치가 보인 건 PR 2분 전뿐이었다. 서비스 저장소 `CONTRIBUTING.md`도 "main에서 작업하다 올릴 때 브랜치로 옮겨도 된다"고 안내한다
- 그래서 브랜치가 안 보여도 PC에서 작업 중일 수 있다. `server/`는 승진, `web/`은 금혁 담당으로 보고, 할 일 문서는 짧게 덧붙이는 정도만 한다
- S1 완료 표시를 `server/NEXT.md`·`AGENTS.md`에도 하려다 사용자가 멈췄다("승진은 알아서 작업하고 있으니 건드리지 마"). 되돌리고 금혁 님 쪽만 고쳤다.
  승진 님 원격 브랜치는 PR #8 말고 없어, 공개된 진척은 S1뿐이다
