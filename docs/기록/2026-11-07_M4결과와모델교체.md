  대신 **습한 날(85~95%) 높게 부르는 버릇은 여섯 개 모두 줄었다**(ⓑ' +1.11 → +0.50, ②-전체 +2.52 → +0.05). "일부만 줄 것"이라던 예상은 틀렸다

- 배포 준비: ONNX 변환(학습 식과 차이 0.00001), 즉석 추론(S5b) 팀장 몫 코드. VM 반영은 사용자 확인 대기

## 배경

11/5 오전까지 M4 사전 등록과 ⓑ 범위 시험(상한 약 3e-4)을 마쳤다. 사용자는 11/5~6 해커톤 중이라 GPU를 하루 종일 쓸 수 있었고, 일은 "표의 한 줄이 끝날 때마다 확인받고 다음으로" 진행했다.
범위는 습도(M4)까지. 교체는 "M5까지 본 뒤 한 번"이었는데, M4 결과를 보고 M5를 할지 정하기로 했다.

## 한 일

### 습도 가중치 학습률 다시 정하기 (11/5)

- 처음 계산("Adam이 매 걸음 학습률만큼 간다"고 보고 필요 거리의 3배)으로 3e-3을 정했는데, 연기 시험(128번, 2바퀴)에서 w가 −0.003만 움직였다(목표 −0.071)
- Claude가 이를 "1/10 속도"라고 보고했지만, 실제 학습 길이로 재 보니 3e-3도 목표의 0.83까지는 갔다. **과장이었다**(아래 정정)
- 고르는 규칙을 먼저 적고(학습된 w ÷ 목표의 중앙값이 1에 가장 가까운 값) 3e-3·1e-2·3e-2를 실제 길이로 돌렸다: 0.83 / **1.06** / 1.10 → 사용자 지시대로 **1e-2**
- 사전 등록 문서에 바꾼 전후와 이유를 함께 적었다(점수를 보기 전)

### ⓑ 학습률 비교 (11/5)

- 규칙(1e-4의 1/3과 3배, 3배가 상한의 1/3을 넘으면 그 아래로)대로 하니 3e-5 하나만 남았다
- 연습시험 3.15 → 3.07(−0.08, 기준 0.05 초과), 묶음 셋 모두 3e-5가 나았다 → ⓑ' = 3e-5
- **풀지 못한 것**: 두 학습률 모두 한도 12바퀴의 마지막이 가장 좋았다. 학습률이 끝에 0으로 줄어드는 일정이라 바로 "바퀴가 모자라다"로 읽지는 않았다. 사용자가 "해결 덜 됐다고 메모만 하고 넘어가자"고 했다

### 결과 읽기와 결정 (11/6)

- 사용자는 ⓑ'+물리식, ⓑ'+그대로, ②-전체+물리식을 "유의미"하다고 봤다. Claude는 규칙상 MAE는 모두 동점이고, 유의미한 것은 습한 날 치우침이며 그건 물리식 쪽에만 해당한다고 바로잡았다(ⓑ'+그대로는 +1.11 → +0.97로 거의 그대로)
- ②-마지막 층은 "운영 방식에 가장 잘 맞는" 후보(몸통은 옛날 날, 마지막 층은 최근 날로 계속 갱신)였지만, 점수가 뒤져(3.07) 사용자가 뺐다
- **M5를 할지**: 사용자는 "일사량·운량은 습한 날 치우침 때문 아니었나? 습도로 셋 다 줄었는데 굳이?"라고 물었다.
  - 기록을 찾아보니 일사량은 10/13 "다음 학습 때로 미룬 것"에만 있고 이유는 적혀 있지 않았다. Claude는 빛(흐린 날 화면이 납작해지는 것)을 겨냥한 것으로 이해했다고 밝혔다(문서 근거 없음)
  - 값싼 확인: M4와 같은 모양으로 ⓑ'+물리식의 연습시험 예측에 일사·운량 기울기를 맞춰 시험에 얹었다. 맑음 정도 2.87 → 2.86, 전운량 2.68 → 2.67
  - 같은 방법으로 ⓑ'에 습도를 얹어 확인 방법 자체를 시험했더니 2.99 → 2.98이었는데, 실제 학습은 2.91이었다. **이 확인은 효과를 못 잡는다**고 보고 그대로 전했다
  - 그래도 사용자는 M5를 건너뛰고 ⓑ'+물리식으로 서비스를 확정했다. 근거: 습도도 0.1을 못 넘었고, 남은 오차는 일사량이 겨냥하는 종류가 아니고(아래), 전시까지 4일이다
- 바퀴 수 한도 시험(약 3시간)은 Claude가 "좋아져도 0.1을 넘기 어렵다"며 미루기를 추천했고, 사용자가 동의했다

### 왜 3 아래로 못 내려가나 (11/6)

사용자가 "왜 3 이하로 파격적으로 못 내려갈까"를 물어, GPU 없이 시험 기간 자료로 계산했다.

| 비교 | 값 |
|---|---|
| 2.6~5km 이웃 측정소끼리 같은 시각 값 차이 (11쌍) | 평균 3.1 |
| 이웃 측정소(카메라에서 평균 4.1km) 실측을 그대로 답으로 | MAE 3.24 |
| 같은 측정소, 한 시간 전 값과 차이 | 평균 2.67 |
| ⓑ'+물리식 | 2.91 |
| 매 시각 도시 전체가 같이 틀린 몫을 알고 빼면 | 2.19 |

- 정답은 측정소 한 점의 1시간 평균이고 사진은 한 순간의 시선 전체다. 2.91은 이미 이 흔들림 근처다. 다만 정확한 바닥은 아니다(카메라가 늘 같은 측정소와 짝이라 그 측정소의 버릇을 일부 배울 수 있다)
- ⓑ'+물리식 치우침: 실측 10 미만 +1.1, 15~25 −2.1(전체 오차의 41%), 25~35 −5.2. **가운데로 몰린다.** 탁한 날 사진이 적어서로 보고, 겨울 자료로 풀 몫으로 적었다(해석, 검증하지 않음)
- 도시 단위 입력(일사량 같은)이 줄일 수 있는 최대가 0.7(2.91 → 2.19)이라는 것도 M5를 건너뛴 근거가 됐다

### 저장소 점검과 배포 준비 (11/6~7)

- 사용자 요청으로 두 저장소의 브랜치를 봤다. 모델·서비스 저장소 모두 `main`만 있고, 열린 PR·포크도 없다. 서비스 저장소는 11/3 팀장 커밋이 마지막이다.
  조원들이 잊은 것 같다고 해서 단톡에 보낼 독촉 문구를 써 줬다(보내는 것은 사용자)

  학습 식(HumNet + `hum_feature`, CPU) 대비 최대 0.00001, 채점 예측(GPU bf16) 대비 평균 0.07 ㎍/㎥. 추정기 전처리는 학습 때와 차이 0
- 밤(19:27)이라 추정할 사진이 없어 교체하기 좋은 때였다. 모델 파일은 VM에 복사했지만, `git push`와 VM `git pull`(실제 반영)은 자동 권한 검사에서 운영 배포로 막혀 사용자 확인을 기다린다
- **S5b 팀장 몫**: `infer_now.py`에 밤·비·습도 95% 거르기, 가린 사진 `/cam/live/` 저장, 정기 추정기와 같은 잠금(종료 코드 75)을 붙였다.
  습도·비는 "찍은 그 분" 값이 아직 없어 최근 10분 안 1분값을 쓴다. 정기 추정과 다른 점이라 문서에 밝혔다(시연용, 저장하지 않음). PC에서 정상·밤·없는 카메라를 확인했다

## 정정된 판단

- **"습도 가중치가 1/10 속도로 움직인다"**(11/5 Claude): 2바퀴 연기 시험만 보고 한 말이었다. 실제 길이로는 3e-3도 목표의 83%까지 갔다. 그래도 사전에 정한 규칙대로 1e-2로 바꿨다
- **"②의 85~95% 치우침은 일부만 줄 것"**(11/5 사전 예상): 훨씬 많이 줄었다(+2.52 → +0.05). 학습 기간의 치우침(+1.83)이 시험 기간(+2.52)보다 작아, 학습 기간에서 배운 습도 칸이 다 못 고칠 것으로 봤는데 틀렸다.
  카메라별 학습된 가중치가 "필요한 거리"의 약 1.7배였다. 몸통이 함께 배운 몫으로 보지만 확인하지 않았다
