## 배경 — 카메라 소스를 정해야 했다

문서에는 선택지가 `UTIC 유지` vs `ITS 전환`으로 적혀 있었다. 판단 기준은 이랬다.

| | UTIC/fitic | ITS |
|---|---|---|
| URL 확보 | 수동 (개발자도구) | API가 직접 반환 |
| URL 수명 | 고정 | 암호화 토큰, 만료 가능 |
| 화각 | 도심 교차로 | 고속도로·국도 |

그런데 이 표는 **4개 항목 중 3개가 API 편의**였다. 핵심 가설이 "원거리 피사체의 대비 저하"인데
정작 **화각을 제대로 따지지 않고 있었다.**

### 쓰고 있던 카메라가 가설에 맞지 않았다

2주차 MVP로 모은 이미지 119장으로 용현사거리의 화각을 확인했다.

| 용현사거리 | |
|---|---|
| 하늘 비중 | 거의 0% |
| 최원거리 피사체 | 도로 소실점 부근 건물, 수백 m |
| 원거리 지형 | 없음 |

대비 감쇠는 관측 거리에 지수적으로 누적되는데, 거리가 수백 m면 농도가 변해도 대비 변화량이 매우 작다.
반면 **조명 변동은 그대로 크다** — 08시 저각 직사광의 강한 명암 vs 12시 평탄.
신호보다 잡음이 큰 화각이었다.

## 한 일

### 발견 — fitic 목록을 API로 받을 수 있었다

"URL을 수동으로 캐야 한다"는 전제가 사실인지 확인하려고 지도 페이지의 네트워크 요청을 살펴봤다.

```
POST https://www.fitic.go.kr/gis/selectListData.do
body: type=cctv&keyword=
```

응답에 **이름·좌표·스트림 주소가 전부** 들어 있었다. 인천 전역 237대.

```json
{"CCTV_MNGM_NMBR":113, "CCTV_NM":"송도1교사거리",
 "X_CRDN":126.666945, "Y_CRDN":37.392985,
 "HTTPADDR":"http://61.40.94.13:1935/cctv/L804.stream/playlist.m3u8"}
```

이것으로 **선택지의 전제가 무너졌다.** 개발자도구 수작업이 사라졌고, UTIC은 수집에서 완전히 빠졌다.
(응답이 문자열 안에 JSON이 든 이중 인코딩이라 두 번 파싱해야 한다.)

### 화각 자동 스크리닝

237대를 눈으로 보는 건 불가능해서, 수동으로 13대를 평가하며 만든 기준을 코드로 옮겼다.

**프레임 1장에서 계산하는 지표**

| 지표 | 통과선 | 의미 |
|---|---|---|
| 하늘 면적 | 화면의 5% 이상 | 대비 측정의 기준 배경 |
| 하늘 가로 균일도 | p85−p15 ≤ 15 | 얼룩지면 기준이 안 됨 |
| 하늘 포화 | 240 이상 픽셀 비율 | 날아가면 정보 없음 |
| 원경 최저 대비 | 낮을수록 좋음(음수는 실격) | 소실 구간이 있는가 |
| 해상도 | 960폭 미만 감점 | 원경 디테일 |

전체 237대 촬영·채점에 6분, 저장된 프레임으로 재채점하면 5초다.
기준을 바꿔가며 바로 다시 볼 수 있게 만든 것이 검수에 크게 도움이 됐다.

### 검수에서 잡아낸 오류 세 가지

상위 30대를 육안 검수하면서 지적받은 항목을 추적해 기준을 고쳤다.

1. **하늘 면적 기준이 없었다** — 산 위 얇은 조각(화면의 3%)도 통과했다
2. **균일도 계산이 틀렸다** — 2D 전체로 재니 하늘의 자연스러운 위아래 그라데이션까지 불균일로 잡혔다.
   행별 가로 균일도의 중앙값으로 바꾸자 멀쩡한 카메라의 점수가 정상화됐다(21 → 6)
3. **PTZ를 못 걸렀다** — 시간 간격을 둔 두 프레임을 비교하되, 차량 통행 영향을 없애려
   **상단(하늘·지평선)만** 비교하도록 하자 −0.16 / 0.45 vs 0.92 이상으로 깨끗하게 갈렸다

## 확인한 것

### API 제약

라벨 수집을 설계하기 전에 제약부터 재봤다.

| | 백필 | 게시 지연 | 결론 |
|---|---|---|---|
| 기상청 초단기실황 | **1일치뿐** | 매시 40분쯤 | **상시 수집 필요** |
| 에어코리아 PM2.5 | 3개월 | 매시 15분쯤 | 배치로 충분 |

이 차이가 설계를 갈랐다. **PM2.5 상시 수집기는 만들 필요가 없었다.**
당초 계획은 상시 프로세스 3개(이미지·PM2.5·기상)였는데, **상시 1개 + 배치 1개**로 줄었다.
감시할 대상이 3분의 1이 된 셈이다.

에어코리아 약관에서 두 가지를 새로 확인했다.
- 제5조: 활용은 자료 범위 3개월까지. 그 이상은 대기환경월보 확정 데이터
- 제8조: 결과물에 **"인증을 받지 않은 실시간자료"임을 명시해야 함**

`pm25Value`가 1시간 평균인지 정시 순간값인지는 **공식 문서 8종 어디에도 없었다.**
측정소가 하나뿐인 옹진군으로 교차 확인해봤으나, 그 경우 "시간축 평균"과 "공간 평균" 두 해석이
같은 답을 내서 결정적이지 않았다. 미확인으로 남겼다.

### 수집 주기 — 지도교수 지적을 반영한 방식

> "PM2.5 라벨이 1시간 단위인데 10분마다 찍는 건 의미가 없지 않나"

맞는 지적이다. 시간당 6장은 라벨이 같아 독립 샘플이 아니고,
무작위로 train/test를 나누면 근접 프레임이 양쪽에 걸려 성능이 부풀려진다.

다만 **1시간에 1장은 위험하다.** 한 번 실패하면 그 시간이 영구 손실이고,
차량 가림·시각 정렬 문제에도 대응할 수 없다.

그래서 이렇게 정리했다.

> **수집 주기 ≠ 학습 샘플링 주기**
> 수집은 20분(시간당 3장, 결측·가림 보험), 학습은 시간당 1샘플로 집계하거나 대표 1장 선택.
> train/test는 날짜 기준으로 분할.

### 측정소 매칭

카메라 20대에 최근접 **도시대기** 측정소를 붙이면 13곳, 하루 312건(한도 500).
대부분 1~3km 이내였다.

**도로변대기는 제외했다.** 도로 옆이라 차량 배기로 농도가 국지적으로 튀는데,
우리 이미지는 수 km 시선 경로의 공기를 적분한 값이라 성격이 정반대다.

**을왕해수욕장은 이 단계에서 뺐다.** 최근접 측정소가 11.4km로 나머지(1~3km)와 차이가 컸고,
영종·용유도에 대안 측정소가 없었다. 라벨을 못 믿는 카메라를 넣으면
나중에 오차 원인이 화각인지 라벨인지 구분되지 않는다. → **21대 → 20대**
