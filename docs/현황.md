### 주기를 20분으로 정한 이유

PM2.5 라벨이 1시간 단위라 시간당 6장(10분 간격)은 독립 샘플이 아니다.
그렇다고 1시간에 1장이면 **한 번 실패할 때 그 시간이 영구 손실**이고, 차량 가림·시각 정렬에도 대응 못 한다.

> **수집 주기 ≠ 학습 샘플링 주기**
> 수집은 시간당 3장(결측·가림 보험), 학습은 시간당 1샘플로 집계하거나 대표 1장 선택.
> **train/test는 무작위가 아니라 날짜 기준으로 분할할 것** — 근접 프레임이 양쪽에 걸리면 성능이 부풀려진다.

### 프로세스 구성 — 상시 1개 + 배치 1개

백필 가능 여부로 갈린다. **지나가면 사라지는 것만 상시로 받는다.**

```
[상시] collect_cctv.py   이미지(20분)                      ← 백필 불가
[배치] build_labels.py   기상(AWS 1분)·PM2.5 백필 + 병합   ← 언제든 다시 돌릴 수 있다 (2026-10-01 구현)
                         → labels.csv                      PM2.5만 3개월 상한
```

**학습용 기상값은 `build_labels.py`가 PM2.5와 함께 소급해서 받는다**(2026-10-01 결정).
기상청 API허브 AWS 매분자료가 과거 조회되고 1분 단위라, 20분 사진 전부에 같은 분의 값을 붙일 수 있다.
9/21부터 쌓인 사진에도 그대로 적용된다.
수집기가 매시 받는 초단기실황(`weather.csv`)은 그 정각 값의 부분집합이므로 **학습에 쓰지 않는다.**
대신 **검증용으로 계속 수집한다.** 1분 API로 받은 값의 정각 값을 `weather.csv`와 대조하면
수집 기간 전체를 확인할 수 있다. 매칭 기준으로 고른 관측소 7곳이 실황 격자가 쓰는 7곳과 같아서 빠지는 관측소가 없다.
비용은 무시할 수준이다(공공데이터포털 무료, 4개월 약 4MB).

**기상·측정소 매칭은 수집기 쪽이 맡는다.** 백엔드 조원도 같은 일을 만들고 있어 겹쳤는데,
수집기 쪽으로 일원화하기로 했다(2026-10-01).

### 병합 원칙 — 시각이 일치하지 않으면 결측으로 둔다

**사진에 붙이는 기상값과 PM2.5는 시각이 정확히 일치하는 것만 쓴다.**
가까운 시각 값으로 메우지 않는다. `build_labels.py`에 최근접 시각 조인을 넣지 않는다.
PM2.5는 1시간 평균값이라 "일치"를 **사진 시각이 평균 구간 안에 드는가**로 판단한다(§6).

방어 논리 때문만이 아니다. 기상값의 첫 용도가 **필터링**(강수·고습 프레임 제거)인데,
14시에 비가 시작됐는데 13시 `PTY=0`을 붙이면 비 오는 프레임이 깨끗한 것으로 통과한다.
오차가 조금 커지는 정도가 아니라 **필터가 반대로 동작하고**, 그 프레임은
"PM2.5는 낮은데 시야가 흐린" 사례가 되어 모델을 거꾸로 가르친다.

수집기에도 같은 원칙을 적용했다(2026-09-22). 이전에는 해당 시각 자료를 못 받으면
직전 시간으로 물러나 받았는데, 한 시간 전에 이미 받아둔 자료가 중복되는 대신
정작 비어 있는 시각은 성공으로 집계되어 결측이 드러나지 않았다.
지금은 **같은 시각으로 두 번 시도하고, 못 받으면 결측 행을 남기고 즉시 알린다.**

## 3. 검증된 사실 (재확인 불필요)

**데이터 소스**

1. **fitic 카메라 목록을 API로 받을 수 있다**
   ```
   POST https://www.fitic.go.kr/gis/selectListData.do
   body: type=cctv&keyword=
   ```
   - 응답이 **이중 인코딩**(문자열 안에 JSON)이라 두 번 파싱해야 함
   - 필드: `CCTV_MNGM_NMBR`(번호) `CCTV_NM`(이름) `X_CRDN`(경도) `Y_CRDN`(위도) `HTTPADDR`(스트림)
   - 인천 전역 237대. `HTTPADDR`의 `http://61.40.94.13:1935` → `https://cctv.fitic.go.kr`로 치환
   - 공식 오픈 API가 아니라 지도 페이지 내부 엔드포인트이므로 **목록 조회는 하루 1회 수준으로만**

2. **실제 스트림 해상도** — 960×540이 150대, 1280×720이 60대, 640×360 이하 18대.
   브라우저 플레이어로 보면 커 보이지만 업스케일이다

3. **클라우드 IP에서 접속 가능** — 해외 IP·데이터센터 IP 차단 없음, Referer 검사 없음

**라벨 소스**

4. **기상청 초단기실황은 백필 불가 — 최근 1일치뿐.** 1일 전부터 `"최근 1일 간의 자료만 제공합니다"`
   - 단 **API허브 AWS 매분자료는 소급된다**(§8). 학습용 기상은 그쪽을 쓴다
   - 자료는 매시 정시 기준, 게시는 매시 40분쯤
   - 격자 변환(Lambert)은 서울 종로(60,127)·인천 미추홀(54,124)·제주(53,38)로 검증 완료
   - **`:40`에 받으면 같은 시각 자료를 받을 수 있다** — 12시간 연속으로 격자 13개씩
     빠짐없이 수집됐다(2026-09-22 00~11시). 대체 시각으로 물러난 경우 0건

5. **에어코리아 PM2.5는 3개월 소급 가능.** 단 **활용은 3개월 범위가 상한**이며
   그 이상은 국립환경과학원 대기환경월보의 확정 데이터를 써야 한다 → **월 1회 백필은 필수 운영 규칙**
   - 근거는 OpenAPI 기술문서 §3.2 준수사항 (5). 거기서 "약관 제5조"를 들지만 약관 제5조 본문(금지사항)에는 3개월 언급이 없다

6. **에어코리아 생성주기 매시 15분 내외.** `dataTime=13:00` 자료는 13:15쯤 게시된다
   → 라벨 병합은 수집과 분리된 후처리여야 한다

7. **에어코리아 측정소 목록은 위경도를 준다** — TM 변환 불필요.
   `getMsrstnList`의 `dmX`=위도, `dmY`=경도. `mangName`으로 도시대기/도로변대기/항만/교외 구분

**환경**

8. **이미지는 소급 불가** — 과거 스트림을 제공하는 곳이 없다. 수집 가동률이 곧 데이터셋 크기
   - 실측 장당 **271KB**(카메라 20대 평균). 낮 길이에 따라 하루 600~720장
9. **Ubuntu 22.04는 사용 불가** — Python 3.10이라 `tomllib`(3.11+)이 없다. 24.04 사용
10. **fitic 쪽에서 카메라가 한꺼번에 죽는 날이 있다** — 9/27 07시대부터 해 질 때까지 20대 중 18대가
    `스트림 열기 실패`였다(그날 성공 107장, 평소 약 700장). 우리 쪽 문제였다면 20대가 다 실패했어야 하므로 스트림 서버 쪽으로 본다(원인 미확인).
    이런 날은 이미지가 영구 손실이라 데이터셋에서 빠진다

## 4. 카메라와 측정소

`Tools/screen_fitic.py`로 237대를 자동 채점 후 육안 검수해 **20대**를 확정했다.
목록은 `Collector/cameras.toml`, 선정 과정은 [기록/2026-09-21](기록/2026-09-21_카메라선정과배포.md).

**판정 기준** — 하늘 면적 5% 이상 · 하늘 가로 균일도(p85−p15) 15 이하 · 포화율 · 원경 최저 대비(음수는 실격) · 해상도

**측정소 매칭** — 최근접 **도시대기** 측정소 13곳, 하루 312건(한도 500). 대부분 1~3km, 최장 4.0km.

도로변대기를 쓰지 않는 이유: 도로 옆이라 차량 배기로 농도가 국지적으로 튄다.
우리 이미지는 **수 km 시선 경로의 공기를 적분한 값**이라 성격이 정반대다.

**한계로 남겨둘 것**: 이미지는 카메라 지점이 아니라 시선 경로 전체의 공기를 보는데 라벨은 측정소 한 점의 값이다.
인천은 측정소가 촘촘해 차이가 크지 않을 것으로 보지만, 특정 카메라만 오차가 클 때 원인 후보로 둘 것.

**주의**: 원경 타겟은 **건물이 안전하다.** 산림은 9~11월 단풍·낙엽으로 반사율이 바뀌어 수집 기간과 겹친다.

```
python Tools/screen_fitic.py              전체 촬영 후 채점 (약 6분)
python Tools/screen_fitic.py --rescore    저장된 프레임 재채점 (약 5초)
python Tools/screen_fitic.py --ptz-check  화각 변경 검출 (시간 간격이 클수록 정확)
```

## 6. `pm25Value`는 기준시각 **직전 1시간의 평균**이다 (2026-10-01 확인)

API 명세에는 없고, 「대기환경측정망 설치·운영지침(2025)」(환경부·국립환경과학원, 에어코리아 자료실)에 있다.

- **p.16 표3** — PM-2.5 측정주기는 **1시간(일부 장비만 매 5분)**, 자료는 **1시간 농도값**으로 생성한다.
  대부분의 장비는 1시간 동안 입자를 모아 한 번 재므로 **원천적으로 순간값이 없다**
- **p.171 별표6-1** — 측정망 내부는 시작 시각으로 표기하지만,
  *"에어코리아와 NAMIS는 1시간 자료에 한해 Endtime으로 사용"*. 예시: 02:00:00~02:59:59 → **03시 자료**
- `dataTime`에 `24:00`이 나오는 것도 같은 규칙이다(23:00~23:59 평균). 시작 시각 표기라면 24시는 나올 수 없다

```
dataTime 12:00  =  11:00:00 ~ 11:59:59 평균
                   → 이 구간 사진: 11:00 · 11:20 · 11:40
                   → 12:00 사진은 dataTime 13:00에 속한다
```

**"사진이 찍힌 순간의 PM2.5"는 존재하지 않는다.** 공개되는 가장 짧은 단위가 1시간 평균이다.
따라서 PM2.5 병합은 시각 일치가 아니라 **사진 시각이 평균 구간 안에 드는가**로 판단한다.

기상은 성격이 다르다. 학습에 쓰는 AWS 매분자료는 **사진과 같은 분의 1분 평균값**이라 시각을 정확히 맞출 수 있다(§8).

  121번은 **10/9 하루 종일**(가장 탁한 날) 다른 화각이었다. 124번은 고정 위치가 둘인데 둘째 위치는 같은 장면으로 보고 남긴다
- **깨진 화면** — 10042번 10/8 06:40~08:20 회색·깨진 화면 6장, 87·113번의 **아래쪽 세로 번짐** 2장(전송 중 영상 손실, 위쪽은 멀쩡함)
- **해상도 변경** — 10042번이 깨짐 직후 1280×720 → 640×360. 화각은 같지만 바뀐 뒤 선명도가 28% 올랐다(다른 카메라는 그대로, PM2.5는 오히려 높음).
  그래서 **장면 = 카메라@해상도**로 묶어, 기준 사진·글자 가림·특징 표준화를 장면마다 따로 한다

**판단 방식** — 아래 셋 다 검수 결과와 대조하며 정했다
1. **윤곽선이 평소와 닮았는지로 재지 않는다.** 먼지가 먼 건물 윤곽을 지워 뿌연 사진이 화각 변경처럼 나온다(그 기준으로 걸린 727장의 PM2.5 평균 16.2, 나머지 12.6)
2. **특징점(ORB)이 평소 자리에 있는지**로 잰다. 이때 **화면 위 글자(지명 표시)를 가린다** — 카메라가 돌아가도 글자는 제자리라,
   가리지 않으면 사람이 뺀 165장 중 77장이 이동 0~2픽셀로 나왔다. 글자 자리는 장면마다 사진 150장을 겹쳐 모든 사진에서 같은 픽셀로 찾는다(`Model/view_mask/`)
3. **구간으로 판단한다.** 역광·어둠·연무로 특징점이 적은 사진(131번 아침, 212·13번 해 질 녘)이 혼자 "옮겨 갔다"로 나오는 문제가 있었다.
   20분 간격 사진끼리 잘 맞으면 한 구간으로 묶고, 구간 안에서 확실히 맞춰진 사진의 다수결로 구간 전체를 정한다

| 방식 | 사람이 뺀 165장 중 잡음 | 사람이 남긴 사진을 뺌 |
|---|---|---|
| 10/10 (글자 안 가림, 20픽셀) | 88 | 17 |
| 글자 가림 | 162 | 55 |
| **글자 가림 + 구간 판단 (지금)** | **164** | **4** |

남은 차이 5장(사람만 1, 자동만 4)은 사진을 다시 보니 모두 사람 쪽 오류여서 검수 결과를 고쳤다. 지금은 168장이 완전히 일치한다.

번짐은 아래쪽 60% 안에서 위아래 줄이 같은 구간을 잰다. 11,420장 중 번짐이 있는 사진은 정확히 8장(위의 깨짐 8장)이고 나머지는 0이다.

### CNN 설계 (2026-10-11 확정)

`Model/cnn.py`. 아직 학습 결과는 없다.

**모델을 둘로 나눈다** — 최종 목적이 인천 예측이라서.
- **인천 ver**: 인천 사진만. 지금~가을(0~50 범위)에 강할 것으로 예상, 학기 성과 정리용
- **인천+베이징 ver**: 인천 개발 날짜 + 베이징 학습 날짜를 **섞어서** 한 번에 학습. 황사·고농도 시즌 대비.
  10/10 계획의 "외부 → 인천" 순서 학습은 뺐다 — 인천(저농도)으로 마무리하는 동안 고농도 감각을 잊을 수 있어 이 버전의 목적과 맞지 않는다

**진행** — 단계는 칼같이 나누지 않고, 각 단계 안에서 후보를 비교해 고른다.
`0. 베이스라인 → 1. CNN 사진 전체 → 2. ROI 찾기(카메라마다 직접 상자 지정, 후보 여럿) → 3. 기상 고르기(어떤 기상을 넣을지, ROI와의 조합 포함)`.
후보는 먼저 사전학습 CNN이 뽑은 특징 + Ridge로 빠르게 거르고(후보당 1~2분), 상위만 실제 학습한다.
예선용 축소(224 크기·연습시험 1묶음)는 고르는 정확도를 내주는 방식이라 쓰지 않는다(사용자 결정)

| 항목 | 결정 |
|---|---|
| 모델 | `convnextv2_tiny.fcmae_ft_in22k_in1k_384` (timm, 28.6M) |
| 입력 | 사진 전체를 **384×384로 늘이거나 줄여** 맞춘다(인천 가로·베이징 세로 모두). 사전학습도 같은 방식(squash) |
| 카메라·도시 정보 | **주지 않는다.** "베이징이면 높게"라는 지름길을 배우면 인천에 고농도가 와도 낮게 부른다. 최후의 보루로 남김 |
| 정답 형태 | 인천 ver은 농도 그대로, **인천+베이징 ver은 log(1+PM2.5)** — 베이징 200대의 큰 오차가 학습을 장악하지 않게. 점수는 원래 농도로 |
| 증강 | 사진마다 살짝 잘라내기(최대 8%)·반 확률 좌우 뒤집기만. 색·밝기 변형 금지 |
| 연습시험 | 개발 14일을 날짜 번호 % 4 (0·1·2)로 **3묶음**. 베이스라인도 같은 묶음으로 다시 채점(`baseline.py --cv3`): 이미지만 **4.56**, 평균만 5.96 |
| 바퀴 수(에폭) | 최대 15바퀴, 매 바퀴 연습시험 → 오차가 가장 작은 바퀴. 최종 모델은 같은 학습 일정으로 그 바퀴에서 멈춘다 |
| 시험지 A | 인천 4일(변동 없음). **모든 작업이 끝난 뒤 한 번만** 연다(`cnn.py --test`) |
| 시험지 B | 베이징 첫날(2019-05-19)부터 날짜 번호 % 4 == 3인 날(67일 1,301장). 어느 버전도 학습에 쓰지 않는 고농도 참고 시험 |
| 학습 설정 | 묶음 16장, AdamW 1e-4, 가중치 감쇠 0.05, 1바퀴 준비 + 코사인 감소, bf16 혼합 정밀도, L1 손실, drop path 0.1 |

거르기 후 학습 자료: 인천 개발 14일 8,154장(PM2.5 평균 12.7, 최대 48), 시험지 A 2,295장, 베이징 학습 206일 4,123장(평균 40.1, 최대 262).

**속도 (3060 Ti 실측, 2026-10-11)**
- timm의 V2 전용 층(GRN)을 같은 식으로 계산 순서만 바꿔 **초당 63 → 90장**. 결과는 fp32 대비 차이가 원래 방식과 같다(2.2%, 1위 일치 100%)
- 묶음 16장에 GPU 메모리 5.8GB. 32장은 넘친다
- 예상 소요: 후보 하나에 인천 ver 약 1.1시간, 인천+베이징 ver 약 1.8시간. 계획한 후보(버전마다 7개) 전부 약 18~21시간
- **GPU를 같이 쓰는 프로그램(게임 등)을 켜 두면 몇 분의 1로 느려진다.** 메모리가 넘치면 Windows가 PC 메모리를 빌려 수십 배 느려지므로
  코드에서 상한(80%)을 걸어 그 전에 오류가 나게 했다
- 384로 줄인 사본(15,873장, 7GB)을 `data/model/cnn_cache/`에 한 번 만들어 두고 매 바퀴 읽는다(39초에 생성)

### 모델 계획 (2026-10-10 확정)

학습은 **로컬 GPU(RTX 3060 Ti 8GB)**에서 한다. VM(e2-micro)은 학습 불가.

| 단계 | 내용 |
|---|---|
| 거르기 | 강수(`rain=1`), 고습도(**95% 이상**, 10/10 결정), PM2.5 결측, **화각 변경·깨진 화면**(10/10, 사람 검토) |
| ROI | 하늘·원경 건물. **처음엔 사진 전체로** 베이스라인을 돌리고 결과를 본 뒤 지정 |
| 베이스라인 | 대비·채도·암채널·선명도·하늘-원경 밝기차 + 습도·태양고도 → 회귀. **가설 검증 지점** |
| CNN | 사전학습 백본(ConvNeXt V2-Tiny) + 회귀 헤드 미세조정. **색·밝기 증강 금지**(색과 대비가 정답 신호). 세부는 아래 CNN 설계 절(10/11) |
| 기상 결합 | 이미지 특징 + 습도·기온·풍속·태양고도 |

**평가**
- 날짜 단위 분할. 무작위 분할 금지
- MAE·RMSE와 함께 **평균만 찍는 모델 대비 개선폭**
- 같은 시간 사진 3장의 예측 평균을 1시간 정답과 비교하는 방식도 함께
- 시험지 둘: **A. 인천 시험**(본 성적, 모든 실험에서 동일) / **B. 고농도 참고 시험**(외부 데이터 중 학습에 안 쓴 날짜)

**외부 데이터 결합** — 인천 단독 결과를 기준점으로 먼저 만든 뒤 비교한다.
"인천 → 외부" 순서는 인천 성적이 떨어질 수 있어 쓰지 않는다. **"외부 → 인천"과 "섞어서"를 둘 다 해 보고**
A가 기준점보다 나빠지지 않고 B가 좋아지는 쪽을 고른다. → 10/11 변경: 인천 ver과 인천+베이징 ver(섞어서)을 둘 다 남긴다(위 CNN 설계). 외부 데이터도 같은 카메라 안에 맑은 날과 탁한 날이
함께 있어야 한다 — 아니면 모델이 흐림 대신 "어느 도시 장면인가"를 외운다.
외부 데이터를 못 쓰게 되면 "0~35 범위에서 검증"을 한계로 밝힌다.

### 서비스 형태 (2026-10-10 확정)

```
[VM]  수집기 (그대로)  → 20분마다 사진
      추정기 (별도 프로세스) → 카메라 20대 추정값 → 백엔드
[백엔드 + DB] → 프론트 타임라인 (추정값 + 나중에 채워지는 실측값)
[로컬] 주 1회 정도 재학습 → 시험 점수가 나을 때만 VM 모델 교체
```

- **수집할 때마다 학습은 불가.** 정답(1시간 평균)이 약 1시간 뒤 게시되므로 찍는 순간에는 학습할 짝이 없다
- 추정기를 수집기와 분리하는 이유: 추정 쪽 오류로 수집이 멈추면 그 시간 이미지는 영구 손실이다
- VM에서 CNN이 메모리(1GB)에 들어가는지는 미확인. ONNX 변환 또는 VM 사양 상향
- **밤**: 사진이 없으므로 측정소 실측값을 IDW로 보간해 보여 준다. 낮(CCTV 추정)과 구분 표시, 몇 시 기준 값인지 표시,
  경계는 경기도 도시대기 측정소 포함
- 모델 값과 IDW 격자는 **"우리가 계산한 값"으로 표시**한다(§9)
- 백엔드 조원과 정할 것: 전송 방식, 백엔드·DB 위치, 저장 항목(실측값 칸 포함), 밤 화면

**GCS 동기화를 1순위에서 내렸다.** 디스크를 실측하니 **모델 마감과 디스크 압박이 겹치지 않는다.**

| 시점 | 총 사용 | 여유 25GB 대비 |
|---|---|---|
| 11/11 (모델 마감) | 13GB / 29GB | 36% |
| 1/31 (수집 종료) | 26GB / 29GB | **90%** |

이전 추정(4개월 18GB)보다 누적량은 20% 늘었지만, 문제가 되는 시점은 12월 이후다.
그때는 모델 작업이 끝나 있다. 대신 일일 요약에 디스크 사용률을 넣고 80%에서
경고가 오게 해뒀으므로, 방치 상태로 차는 일은 없다.

**수집이 끝나길 기다리지 말 것.** 2주치만 있어도 베이스라인을 돌릴 수 있고,
거기서 *"이미지 통계가 PM2.5와 실제로 상관이 있는가"* 라는 가설 자체가 검증된다.
상관이 안 나오면 방향을 틀 시간이 필요하다.

## 9. 출처 표기 의무

결과보고서·발표자료에 반영해야 한다.

- CCTV 영상: **인천교통정보센터**
- 대기오염 정보: **환경부/한국환경공단 에어코리아**, 공공누리 제3유형(출처표시 + 변경금지) (활용약관 제7조)
- 에어코리아 자료는 **"인증을 받지 않은 실시간자료"**로 오류가 있을 수 있음을 명시 (활용약관 제8조, 준수사항 (2))
- 모델 추정값과 IDW 보간 격자는 에어코리아 값이 아니라 **우리가 계산한 값**임을 표시한다.
  "변경금지"가 보간에 어떻게 적용되는지 공식 기준이 없어, 측정값은 그대로 두고 계산값은 구분하는 것으로 정했다(2026-10-10)
- 외부 데이터셋을 쓰면 해당 논문 인용 (§5)
- CNN 사전학습 가중치: **ConvNeXt V2-Tiny (Meta, Woo et al. 2023, arXiv:2301.00808)**, `convnextv2_tiny.fcmae_ft_in22k_in1k_384`.
  가중치는 **CC-BY-NC 4.0**(비상업·출처 표기), 코드(timm, ConvNeXt-V2 저장소)는 MIT. Hugging Face 모델 페이지와 원 저장소 README에서 확인(2026-10-11).
  상업적으로 쓰려면 가중치를 바꿔야 한다
