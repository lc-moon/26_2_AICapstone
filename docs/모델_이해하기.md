# 모델 이해하기

> **AI를 처음 접하는 사람이 우리 모델을 이해하기 위한 문서.** 조원 설명용이자 공부용이다.
> 무엇을 왜 이렇게 했는지를 쉬운 말로 푼다. 정확한 사양과 최신 수치는 `현황.md`가 기준이다.
> 이 문서의 숫자는 **언제 기준인지 날짜를 붙여 둔다.**
> 갱신: 2026-10-11 (베이스라인·화각 전수 검수까지)
> 모델 작업이 끝나면 이 문서를 웹페이지로 옮긴다(`현황.md` §7 다음 작업 4번). 그때까지는 고치기 쉬운 마크다운으로 둔다.

## 1. 한눈에

**CCTV 사진 한 장을 보고 "지금 PM2.5가 몇 ㎍/㎥인지" 숫자로 맞히는 프로그램**을 만든다.

```
[CCTV 사진] ──→ [모델] ──→ "17㎍/㎥"
```

**모델**은 "사진을 넣으면 숫자를 내놓는 계산 장치"다. 처음부터 계산법을 아는 게 아니라,
**사진과 정답을 많이 보여 주면 스스로 계산법을 맞춰 간다.** 이 과정을 **학습**이라고 한다.

학생이 시험 공부하는 것과 같다.

| 학생 | 우리 모델 |
|---|---|
| 문제집 | CCTV 사진 |
| 정답지 | 측정소의 실제 PM2.5 값 (에어코리아) |
| 공부 | 학습 |
| 시험 | 처음 보는 사진으로 맞혀 보기 |
| 점수 | 평균 오차 (MAE) — 작을수록 좋다 |

**가설은 "먼지가 많으면 먼 건물이 뿌옇게 보인다"**이다. 공기 중 입자가 빛을 흩뜨려서,
먼 곳일수록 대비가 떨어지고 색이 바랜다. 모델이 이 뿌연 정도를 보고 농도를 맞히게 하는 것이 목표다.

## 2. 문제집과 정답지 — 데이터

### 문제집: CCTV 사진

- 인천 CCTV **20대**에서 **20분마다** 1장씩 찍는다. 밤(해가 진 뒤)은 조명이 달라 찍지 않는다
- 하루 카메라 1대당 30여 장, 20대면 하루 600~700장
- 카메라는 하늘과 먼 건물이 보이는 곳으로 골랐다(237대 중 20대)

### 정답지: PM2.5 값

- 사진 근처 **에어코리아 측정소**(대부분 1~3km)의 값을 정답으로 쓴다
- 이 값은 **1시간 평균**이다. "사진이 찍힌 순간의 농도"는 측정기가 애초에 만들지 않는다.
  그래서 11:00·11:20·11:40 사진 3장이 같은 정답(11시대 평균)을 공유한다
- 사진마다 정답을 붙인 것을 **라벨**이라고 한다. `Tools/build_labels.py`가 이 일을 한다

### 같이 붙이는 것: 날씨

- 사진을 **찍은 그 분**의 습도·기온·풍속·비 감지 값(기상청 1분 자료)을 붙인다
- 습도가 높아도, 비가 와도 사진이 뿌옇게 된다. 먼지 때문인지 날씨 때문인지 구분하려면 날씨를 알아야 한다

### 지키는 원칙: 시각이 안 맞으면 비워 둔다

정답이나 날씨가 비어 있으면 **앞뒤 시간 값으로 메우지 않는다.** 그 사진은 학습에서 뺀다.

> 예: 14시에 비가 오기 시작했는데 13시 값("비 없음")으로 메우면, 비 오는 사진이 "맑은 날 사진"으로 들어간다.
> 모델은 "PM2.5가 낮은데 뿌연 사진"을 보고 거꾸로 배운다. 조금 틀리는 게 아니라 반대로 가르치게 된다.

실제로 정답이 빈 경우가 있다. 9/22~10/9에 측정소 13곳 중 PM2.5가 비어 온 시간이 86시간이었고,
사유는 **전부 "통신장애"**(측정소 → 서버 전송 실패)였다. 이 시간의 사진 305장은 뺐다.

### 사진 수 ≠ 데이터 양

사진은 1만 장이 넘지만, 같은 날 사진끼리는 대기 상태가 거의 같다.
**실제로 서로 다른 "대기 상황"은 날짜 수만큼**이라고 보는 게 맞다. 19일치면 "19번의 경험"에 가깝다.
뒤에 나오는 "날짜 단위로 나누기"가 중요한 이유다.

## 3. 모델을 만드는 순서

```
① 거르기  →  ② ROI  →  ③ 베이스라인  →  ④ CNN  →  ⑤ 기상 결합  →  ⑥ 외부 데이터
  나쁜 사진    볼 곳      단순한 모델      딥러닝      날씨 정보      고농도
  빼기         정하기     (가설 확인)      (본 모델)   더하기         보충
```

| 단계 | 쉽게 말하면 | 왜 하나 |
|---|---|---|
| ① 거르기 | 문제집에서 잘못 인쇄된 문제 빼기 | 비·안개·고장 사진으로 공부하면 잘못 배운다 |
| ② ROI | 사진에서 볼 곳만 오려 내기 | 아래쪽 도로의 차는 먼지와 무관하다. 하늘과 먼 건물만 보게 한다 |
| ③ 베이스라인 | 단순한 방법으로 먼저 풀어 보기 | "사진에 정말 신호가 있나?" 확인 + 나중 모델이 넘어야 할 기준 점수 |
| ④ CNN | 딥러닝 모델로 제대로 풀기 | 사람이 정한 숫자 몇 개보다 훨씬 많은 것을 사진에서 찾아낸다 |
| ⑤ 기상 결합 | 날씨 정보를 같이 주기 | 같은 뿌연 사진이라도 습도가 높으면 먼지 탓이 아닐 수 있다 |
| ⑥ 외부 데이터 | 다른 나라 고농도 사진으로 보충 | 인천은 요즘 공기가 깨끗해 탁한 날 사진이 거의 없다(§7) |

> **2026-10-11에 순서를 바꿨다.** 위 그림은 10/10 계획이다. 실제로는 ② ROI를 CNN 뒤로 옮기고, ⑥ 외부 데이터는 처음부터 CNN에 섞는
> "인천+베이징 ver"으로 따로 만들었다. 지금 순서는 **0 베이스라인 → 1 CNN 사진 전체 → 2 ROI → 3 기상**이고, 단계마다 인천 ver과 인천+베이징 ver을 둘 다 만든다(§6).
> ROI를 뒤로 옮긴 이유: 사진 전체로 학습한 CNN 점수를 기준점으로 삼아야 "ROI가 얼마나 도움이 됐나"를 잴 수 있기 때문이다.

**왜 베이스라인부터?** 바로 CNN으로 가면 점수가 나와도 그게 좋은 건지 알 수 없다.
"단순한 방법으로 이만큼 → CNN으로 이만큼"처럼 **비교할 기준**이 있어야 한다.
또 단순한 방법으로 신호가 전혀 안 보이면, CNN에 시간을 쓰기 전에 방향을 다시 봐야 한다.

## 4. 공정하게 채점하기

모델을 만드는 것보다 **채점을 공정하게 하는 것**이 더 어렵다. 잘못 채점하면 실력보다 좋은 점수가 나와 착각하게 된다.

### 규칙 1. 날짜 단위로 나눈다

11:00 사진으로 공부하고 11:20 사진으로 시험 보면, 같은 날 같은 공기라 **답을 보고 시험 친 셈**이다.
그래서 "이 날짜는 공부용, 저 날짜는 시험용"처럼 **날짜로** 나눈다. 사진을 무작위로 섞어 나누지 않는다.

### 규칙 2. "평균만 부르는 모델"과 비교한다

가을이라 농도가 늘 낮은 범위(대부분 5~20)에 있다. 사진을 안 보고 **"항상 12"**라고만 해도 오차가 작게 나온다.
그래서 점수는 항상 **"평균만 부르기보다 몇 % 나은가"**로 읽는다.

### 규칙 3. 모의고사와 수능을 구분한다

| | 우리 프로젝트 | 언제 보나 |
|---|---|---|
| **모의고사** | 교차검증 (개발용 날짜) | 몇 번이든. 보면서 방법을 바꿔도 된다 |
| **수능** | 시험지 A (따로 떼어 둔 날짜) | **맨 끝에 딱 한 번** |

**왜 수능은 한 번만?** 시험지 A를 보고 "이렇게 바꾸니 점수가 오르네" 하고 고치면,
그 순간 시험지 A는 **연습 문제**가 된다. 시험 문제에 맞춰 공부한 셈이라 점수가 부풀려진다.
실제 서비스에서 처음 보는 날에는 그만큼 못 맞힌다.

```
지금 ──→ CNN ──→ 기상 결합 ──→ 외부 데이터 ──→ [최종 모델 결정] ──→ 시험지 A 개봉 (1번)
         ↑                                                ↑
         이 동안은 전부 교차검증(모의고사)으로만 비교           베이스라인·CNN·최종 모델을
                                                         한꺼번에 채점해 발표용 숫자를 만든다
```

**시험지 A를 고르는 규칙**: 9/22부터 세어 4일마다 하루(9/25, 9/29, 10/3, 10/7, 10/11 …).
날짜가 늘어도 규칙이 같아서 이미 정한 시험일은 바뀌지 않는다. 맑은 날·탁한 날이 고루 섞이는 효과도 있다.

**시험지 B**는 외부 고농도 데이터 중 학습에 안 쓴 날짜다. 탁한 날을 얼마나 맞히는지 보는 참고 성적이다.

### 교차검증 — 돌아가며 모의고사 치기

개발용 날짜(지금 14일) 안에서 하루씩 돌아가며 시험을 친다.

```
1회차:  [9/22 시험]  나머지 13일로 공부
2회차:  [9/23 시험]  나머지 13일로 공부
 ...
14회차: [10/9 시험]  나머지 13일로 공부
          ↓
14번의 점수를 평균 → "교차검증 점수"
```

**왜 번거롭게?** 하루짜리 모의고사를 한 번만 보면 **그날 운**에 좌우된다.
실제로 데이터가 7일치일 때 시험일이 비 온 하루(9/25)뿐이었는데, 그날은 농도 범위가 좁아
평균만 불러도 오차가 2.5밖에 안 나왔다. 그 숫자로는 아무것도 판단할 수 없었다.
14일을 돌아가며 보면 맑은 날·탁한 날·습한 날이 모두 시험에 들어가 점수가 안정된다.

## 5. 베이스라인 — 체크리스트로 판단하기 (2026-10-10)

### 무엇을 하나

**사진에서 사람이 정한 숫자 몇 개를 재고, 그 숫자로 PM2.5를 맞히는 공식을 찾는다.**

```
사진 ──(Model/features.py)──→ 숫자 13개      ──┐
                              대비 0.38         │
                              채도 0.25         ├──(Model/baseline.py, Ridge 회귀)──→ PM2.5 예측
                              암채널 0.23       │
                              ...               │
       날씨 ──────────────→  습도·기온·풍속·태양고도 ──┘
```

**베이스라인도 사진을 본다.** CNN과 다른 점은 **"사진에서 무엇을 볼지 누가 정했나"**다.
베이스라인은 사람이 "대비를 재라, 채도를 재라"고 정해 준 것만 본다.
비유하면 **체크리스트를 들고 사진을 보는 신입**이다.

### 사진에서 재는 숫자

같은 숫자를 **사진 전체**와 **위쪽 1/3 띠**(대개 하늘·먼 건물)에서 따로 잰다.

| 숫자 | 뜻 | 먼지가 많으면 |
|---|---|---|
| 밝기 | 사진이 얼마나 밝은가 | 보정용 |
| 대비 | 밝은 곳과 어두운 곳의 차이 | 줄어든다 (평평해짐) |
| 채도 | 색이 얼마나 진한가 | 줄어든다 (색이 바램) |
| **암채널** | 사진에서 가장 어두운 점들의 밝기 | **올라간다.** 맑으면 그림자 같은 새까만 점이 있는데, 먼지가 끼면 그것까지 희뿌옇게 뜬다 |
| 선명도 | 윤곽선이 얼마나 또렷한가 | 줄어든다 |
| 파랑/빨강 비 | 하늘색 정도 | 줄어든다 (누래짐) |
| 위−가운데 밝기차 | 하늘과 먼 건물의 밝기 차이 | 먼 건물이 하늘에 묻힌다 |

### 거르기

| 뺀 이유 | 장수 |
|---|---|
| 정답(PM2.5) 없음 — 측정소 통신장애 | 305 |
| 비 감지 | 229 |
| 습도 95% 이상 — 안개 위험 | 281 |
| 날씨 값 없음 | 2 |
| 화각이 바뀌었거나 깨진 화면 | 155 |

11,420장 중 **10,448장**이 남았다. 습도 기준은 90%·95%·없음을 비교했는데 점수 차가 거의 없어 안개 위험을 줄이는 95%로 정했다.

**화각이 바뀐 사진**은 관제센터가 카메라를 돌려 다른 곳을 비춘 사진이다. 체크리스트(숫자 13개)는 "그 카메라의 평소 모습과 비교해
얼마나 뿌연가"를 보는데, 다른 곳을 비추면 평소와 비교 자체가 안 된다. 찾는 방법에도 함정이 있었다.
"평소 사진과 윤곽선이 닮았나"로 찾으면 **뿌연 사진이 걸린다** — 먼지가 먼 건물의 윤곽을 지우기 때문이다. 그러면 꼭 필요한 탁한 날 사진을 버리게 된다.
그래서 **모서리 같은 점들이 평소 자리에 있는지**로 찾았다. 뿌옇게 되면 선명함만 떨어지고 위치는 그대로라 영향이 없다.
10/9까지의 사진 11,420장은 **사람이 전부 넘겨보며** 168장을 뺐다. 그 결과로 자동 판단을 고쳤다 — 화면 위 지명 글자는 카메라가 돌아가도 제자리라 가리고 재야 했고, 역광이나 어둠으로 점을 잘 못 찾는 사진은 앞뒤 사진과 묶어서 판단하게 했다. 이제 자동 판단이 사람 판단과 168장 모두 같다. 대조하다가 사람이 놓치거나 잘못 넣은 사진 5장도 찾아 고쳤다. 이렇게 빼자 이미지 모델 오차가 4.91에서 4.57로 줄었다.

**해상도가 바뀐 카메라**도 있었다. 10042번은 10/8부터 스트림 해상도가 절반이 되면서 같은 장면인데도 선명도 값이 달라졌다. 그래서 "평소 모습"을 카메라가 아니라 **카메라@해상도(장면)** 단위로 따로 잡는다.

| 모델 | 무엇을 보고 맞히나 | 평균 오차 | 평균만 대비 |
|---|---|---|---|
| 평균만 | 아무것도 안 봄. 늘 "12.7" | 6.23 | 기준 |

| 기상만 | 날씨만 | 5.15 | 17% 나음 |

| 이미지+기상 | 사진 숫자 + 날씨 | 4.57 | 27% 나음 |

**읽는 법**
- "카메라별 평균"과 "기상만"은 일부러 넣은 비교 대상이다. 동네마다 평소 농도가 다른 것만으로도,
  습한 날 농도가 높은 경향만으로도 어느 정도는 맞힌다. **사진이 그보다 나아야** "사진에 정보가 있다"고 말할 수 있다
- 사진만으로 날씨만 쓴 것보다 잘 맞혔다. **가설이 일단 성립했다**
- 위쪽 띠 숫자만 써도 점수가 같았고(4.86), 사진 전체 숫자만 쓰면 나빠졌다(5.12).
  **신호가 위쪽(하늘·원경)에 몰려 있다** → 다음 단계 ROI의 근거

**습도도 같은 방향으로 흐리게 만든다.** PM2.5가 같아도 습도가 높으면 암채널이 올라갔다.
입자가 습기를 머금어 커지면서 빛을 더 흩뜨리는 것으로 보인다(추정). 그래서 습도는 모델에서 뺄 수 없다.

### 약점: 예측이 평균 쪽으로 쏠린다

| 실제 | 모델 예측 |
|---|---|
| 깨끗한 날 5 | 8쯤 (높게) |
| 보통 날 12 | 12쯤 |
| 탁한 날 25 | 15쯤 (낮게) |

확신이 없는 모델은 "애매하면 평균 근처로 말하자"는 쪽으로 학습된다. 가장 탁했던 10/9(평균 25)를 약 10 낮게 맞혔다.

**왜 문제인가?** 서비스에서 가장 중요한 순간은 **탁한 날**이다. "나쁨"을 알려야 할 때 "보통"이라고 하면 의미가 줄어든다.

| 원인 후보 | 해결책 |
|---|---|
| 탁한 날 사진이 적어 배울 기회가 없다 | 외부 데이터(⑥) |
| 체크리스트(숫자 13개)가 둔하다 | ROI(②), CNN(④) |
| 사진이 원래 그 정도까지만 구분된다 | 한계로 밝힌다 |

베이스라인 자체를 고쳐 쏠림을 없애려는 건 아니다. 다만 원인이 "데이터 부족"이면 CNN에서도 똑같이 나오므로,
어느 원인인지는 짚어 둔다.

## 6. CNN — 경험으로 감을 잡기 (설계 확정 2026-10-11)

### 베이스라인과 무엇이 다른가

```
베이스라인:  사진 → [사람이 짠 계산식] → 숫자 13개 → [공식] → PM2.5
CNN:        사진 → [모델이 통째로 봄] ─────────────────→ PM2.5
```

| | 베이스라인 | CNN |
|---|---|---|
| 사진에서 뭘 볼지 | **사람이 정함** (숫자 13개) | **모델이 스스로 찾음** |
| 배우는 것 | 가중치 수십 개 | 가중치 수백만~수천만 개 |
| 장점 | 빠르고, 왜 그렇게 예측했는지 설명된다 | 사람이 생각 못 한 패턴까지 잡는다 |
| 단점 | 사람이 정한 숫자 밖은 못 본다 | 느리고(GPU 필요) 설명이 어렵다 |
| 비유 | 체크리스트 든 신입 | 경험으로 감을 잡는 베테랑 |

### 처음부터 가르치지 않는다 — 사전학습과 미세조정

CNN을 처음부터 가르치려면 사진이 수십만 장 필요하다. 우리는 그만큼 없다.
그래서 **남이 일반 사진 수백만 장으로 이미 가르쳐 둔 모델**(사전학습 모델)을 가져온다.
이 모델은 "사진 보는 눈"(윤곽, 질감, 색)을 이미 갖고 있다.

여기에 우리 사진을 보여 주며 **PM2.5를 맞히도록 조금 더 가르친다**(미세조정).
영어를 이미 아는 사람에게 의학 영어만 따로 가르치는 것과 비슷하다.

- 쓸 모델: **ConvNeXt V2-Tiny** (사진 보는 몸통 = 백본)
- 끝에 숫자 하나(PM2.5)를 내놓는 작은 부분(회귀 헤드)을 붙인다
- 학습은 로컬 GPU(RTX 3060 Ti)에서 한다

### 주의: 색·밝기를 흔드는 증강은 금지

사진 학습에서는 보통 사진을 뒤집고, 밝기·색을 바꿔 문제집을 늘린다(**증강**).
**우리는 색·밝기 증강을 쓰면 안 된다.** 색과 대비 자체가 정답의 신호라, 그걸 바꾸면 정답을 흔드는 셈이다.
"밝기를 낮춘 맑은 날 사진"은 "탁한 날 사진"처럼 보일 수 있다.

### CNN은 왜 그렇게 예측했는지 설명할 수 있나

| | 설명할 수 있는 것 |
|---|---|
| 베이스라인 | **정확한 이유.** "암채널이 평소보다 높아서 +3, 습도가 높아서 −1 → 15"처럼 공식을 그대로 보여 준다 |
| CNN | **어디를 봤는지 정도.** Grad-CAM 같은 도구로 "사진의 이 부분을 보고 판단했다"를 색칠한 사진(열 지도)으로 보여 줄 수 있다. "왜 그 숫자인가"는 수백만 개 가중치에 흩어져 있어 말로 풀 수 없다 |

열 지도는 발표에 좋은 재료다. **하늘과 먼 건물이 칠해지면** 모델이 가설대로 원경을 보고 판단한다는 근거가 된다.
**도로의 차가 칠해지면** 엉뚱한 걸 배웠다는 경고다.

그래서 두 모델을 같이 둔다. **"베이스라인으로 이유를 설명하고, CNN으로 정확도를 올렸다."**

### 우리가 정한 것 (2026-10-11)

**모델을 두 개 만든다.**

| | 인천 ver | 인천+베이징 ver |
|---|---|---|
| 배우는 사진 | 인천만 | 인천 + 베이징을 섞어서 |
| 잘할 것으로 보는 때 | 지금~가을 (0~50) | 황사·고농도 시즌 |

**차근차근 올린다.** 버전마다 `사진 전체 → ROI 찾기 → 기상 고르기` 순서로 가되, 각 단계 안에서 여러 후보를 비교한다.
예를 들어 ROI는 "하늘만", "먼 건물만", "하늘+먼 건물"을 다 해 보고 가장 나은 것을 고른다.
"어떤 ROI가 가장 나았나"를 찾는 과정 자체가 발표 내용이 된다.

**정한 규칙과 이유**

| 규칙 | 이유 (예시) |
|---|---|
| 사진을 384×384로 늘이거나 줄여 넣는다 | CNN은 한 번에 16장씩 묶어 계산하는데 묶음 안 사진 크기가 같아야 한다. 인천은 가로, 베이징은 세로라 한 크기로 맞춘다. 사전학습 모델도 이렇게 배웠다 |
| 카메라·도시 이름은 알려 주지 않는다 | "베이징이면 높게"를 배우면, 인천에 진짜 황사가 와도 "인천이니까 낮겠지" 하고 낮게 부른다 |
| 인천+베이징 ver은 **로그**로 바꿔 배운다 | 베이징 200을 170으로 틀리면 30, 인천 10을 15로 틀리면 5. 그대로 배우면 베이징 큰 숫자에만 신경 쓴다. 로그로 바꾸면 "몇 % 틀렸나"로 비교돼 두 도시를 고르게 본다 |
| 증강은 살짝 잘라내기·좌우 뒤집기만 | 같은 사진을 매번 조금씩 옮겨 보여 주면 "위치"가 아니라 "뿌연 정도"를 배운다. 뒤집은 사진도 똑같이 뿌옇다 |
| 연습시험은 **날짜 3묶음** | 묶음 둘로 공부하고 하나로 시험, 돌아가며 3번. 하루씩 14번은 CNN에서 너무 오래 걸린다(후보 하나에 약 5~8시간 → 약 1~2시간) |
| 몇 바퀴 배울지는 연습시험이 정한다 | 너무 적게 돌면 덜 배우고, 너무 많이 돌면 학습 사진을 외운다. 매 바퀴 연습시험 점수를 보고 가장 좋은 바퀴에서 멈춘다 |
| 시험지 A는 모든 작업이 끝난 뒤 한 번만 | 시험 점수를 보며 고치면 문제를 미리 본 셈이다 |
| 시험지 B(베이징 4일 중 하루)는 학습에 안 쓴다 | 인천 시험지는 0~48뿐이라 고농도 실력을 못 본다. "인천 ver은 고농도에서 낮게 부르고, 인천+베이징 ver은 따라간다"가 나오면 모델을 둘로 나눈 근거가 된다 |

**같은 기준으로 비교한다.** 베이스라인도 같은 3묶음으로 다시 채점했다. 이미지만 쓴 베이스라인이 **4.56** — CNN이 넘어야 할 숫자다.

### 첫 결과 — 사진 전체 (2026-10-11, 연습시험)

| 모델 | 평균 오차 | 평균만 부르는 모델 대비 |
|---|---|---|
| 베이스라인 (숫자 13개) | 4.56 | 23% 나음 |
| **CNN 인천 ver** | **3.53** | **41% 나음** |
| **CNN 인천+베이징 ver** | **3.43** | **42% 나음** |

- 사진을 통째로 보는 CNN이 사람이 정한 숫자 13개보다 **오차를 약 23% 더 줄였다**
- 베이징을 섞어도 인천 점수가 나빠지지 않았다
- 탁한 날을 낮게 부르는 쏠림은 줄었지만 남아 있다. 25 이상인 사진을 평균 9쯤 낮게 부른다
- 아직 연습시험 점수다. 시험지 A는 모든 작업이 끝난 뒤 연다
- 같은 날 저녁 **화면 위 시각 표시를 가리고**, 베이징 연습시험도 넣어 두 버전을 다시 돌렸다. 이것이 1단계의 최종 기준점이다(위 표의 3.43은 그 전 설계).

| 1단계 최종 (글자 가림) | 인천 오차 | 베이징 오차 |
|---|---|---|
| 인천 ver | 3.47 | 32.2 |
| 인천+베이징 ver | **3.45** | **7.0** |

- 베이징을 섞은 모델은 **인천 성적은 그대로, 베이징 고농도 사진은 거의 맞힌다.** 정답이 평균 190인 사진들을 182로 불렀다(인천만 배운 모델은 20)
- 하지만 **인천의 탁한 날을 낮게 부르는 쏠림은 두 모델이 똑같다.** 베이징 카메라에서 배운 "고농도는 이렇게 보인다"가 인천 카메라로 옮겨 가지는 않았다

### 발견: 모델이 습기를 먼지로 착각한다 (2026-10-11) — 인천에서는 하루치 근거였다는 정정이 아래 "기상 결과"(10/13)에 있다

같은 PM2.5인 사진끼리 비교해도, **습한 날 사진을 더 높게 부른다.** 실제 PM2.5가 0~10인 사진에서 건조한 날은 평균 0.8 높게,
습도 80~95%인 날은 **3.9 높게** 불렀다. 습기를 머금은 공기도 화면을 뿌옇게 만드는데, 모델이 그걸 먼지로 본 것이다.
사용자가 "기상 때문에 흐린 화면을 먼지로 착각하지 않게 하고 싶다"고 했던 걱정이 실제 데이터로 확인됐다.

### 앞으로의 순서

| 단계 | 하는 일 | 방식 |
|---|---|---|
| 2. ROI | 화면의 어느 부분을 볼지 | 후보 8개를 **예선**(빠른 채점)으로 거르고, 좋은 2~3개만 **결선**(진짜 학습) |
| 3. 기상 | 습도 등을 함께 알려 주기 | 후보 3개(습도 / 습도+해 높이 / 기상 4개)를 모두 진짜 학습 |

**예선은 "연습경기"다.** 후보마다 진짜 학습(1~2시간)을 하기엔 시간이 부족하다. 그래서 이미 사진 보는 법을 배운 모델(사전학습 CNN)을 **고치지 않고 그대로** 써서,
사진을 숫자 768개(그 사진에 무엇이 얼마나 있는지)로 요약하고, 그 숫자로 PM2.5를 맞히는 간단한 공식(Ridge)만 만들어 본다. 후보당 1~2분.
연습경기 1등이 시즌 1등이라는 보장은 없어서, 1등 하나가 아니라 2~3개를 결선에 올린다.

**기상은 "같이 보고 판단"하게 붙인다.** 그냥 습도 점수를 더하면 "습하면 늘 몇 점 빼기"밖에 못 한다. 그런데 맑은데 습한 날은 많이 빼야 하고,
먼지로 탁한데 습한 날은 덜 빼야 한다. 그래서 사진 특징과 습도 사이에 작은 판단기 64개를 한 층 넣어, 경우에 따라 다르게 보정하게 했다.
기상을 넣은 뒤에 위의 "습한 날 높게 부르기"가 줄었는지 다시 확인한다.

### ROI 예선 결과와 모델이 본 곳 (2026-10-11 저녁)

- 예선에서 **먼 건물·산**(②), **하늘+먼 건물·산**(③), **아래 도로 빼기**(⑤)가 사진 전체보다 나았다. **하늘만**은 가장 나빴고, 데이터로 자동으로 고른 상자는 사람이 고른 상자보다 나빴다. 이 셋(②③⑤)을 결선에 올린다
- 학습한 CNN이 판단할 때 어디를 봤는지 색칠해 보니(Grad-CAM), 거의 모든 카메라에서 **지평선·먼 빌딩·먼 산**을 보고 있었다.
  **사람이 고른 곳, 데이터가 가리킨 곳, 모델이 본 곳이 모두 같았다** — "먼 곳이 흐려지는 정도로 먼지를 잰다"는 처음 가설과 맞는다
- 예외로 한 카메라(133번)는 도로의 차까지 보고 있었다. 먼지와 상관없는 것이라, 볼 곳을 정해 주는 ROI가 도와줄 수 있다

### ROI 결선 결과 (2026-10-12)

예선 상위 셋을 밤새 진짜로 학습시켜 겨뤘다(두 버전 × 3개, 8시간).

| 볼 곳 | 인천 ver 오차 | 인천+베이징 ver 오차 (인천 / 베이징) |
|---|---|---|
| 사진 전체(1단계) | 3.47 | 3.45 / 7.0 |
| 먼 건물·산만 | 3.53 | 3.50 / 7.26 |
| 하늘+먼 건물·산 | 3.49 | 3.49 / 6.97 |
| **위쪽 60%(아래 도로 빼기)** | **3.37** | **3.42 / 6.97** |

- **두 버전 모두 "위쪽 60%"가 가장 좋았다.** 카메라마다 사람이 정성껏 그린 상자보다, 모든 카메라에서 아래 40%(도로·차)만 잘라 낸 단순한 방법이 나았다
- 다만 차이는 0.1 안팎으로 작다. "ROI가 성적을 크게 올렸다"가 아니라 **"도로를 빼면 조금 낫다"** 정도로 말하는 게 정직하다
- 넓게 남겨 둔 쪽이 이긴 이유로는, 좁은 상자는 모델이 쓸 수 있는 단서(하늘 밝기, 중간 거리 건물 등)까지 잘라 냈을 가능성을 생각할 수 있다. 확인한 사실은 아니다
- 인천+베이징 버전은 세 후보 모두 마지막 바퀴(12번째)가 가장 좋았다. 아직 배우는 중이었다는 뜻이라, 기상 단계부터는 최대 15바퀴로 늘린다
- ROI가 진 이유 확인(10/13): 사람이 그린 상자는 화면의 6~27%뿐이고 위쪽 60%가 21개 장면 중 16개에서 고르게 이겼다. "작아서 정보를 잘라 냈다"는 정황은 있지만,
  상자 크기·찌그러짐과 패배 폭 사이에 뚜렷한 관계는 없어 단정은 못 한다. 선행 과제(건설연)도 아주 작은 ROI로 바꾼 뒤 일부 지표가 나빠졌다

### 기상 결과 — 인천은 날이 모자랐고, 베이징에서는 습도가 통했다 (2026-10-13)

| 기상 | 인천 ver 오차 | 인천+베이징 ver 오차 (인천 / 베이징) |
|---|---|---|
| 없음 | **3.37** | 3.45 / 7.01 |
| 습도 | 3.52 | 3.54 / **6.56** |
| 습도 + 해 높이 | 3.47 | 3.55 / 6.85 |
| 기상 4개 | 3.44 | 3.56 / 6.80 |

- **최종 후보**: 인천 ver은 **위쪽 60%, 기상 없음**. 인천+베이징 ver은 **위쪽 60% + 습도**(인천은 0.1 이내로 지키고 베이징이 가장 좋음)
- 바퀴를 12에서 15로 늘려도 점수는 그대로였다. 같은 설정을 두 번 돌리면 점수가 0.03~0.04 흔들린다는 것도 이때 알았다
- **정정: "습기를 먼지로 착각한다"는 10/11 발견은 인천에서는 사실상 하루(9/26)였다.** 습하고 깨끗한 사진 157장 중 95장이 9/26 아침이었다.
  그날 아침은 습도 80~94%에 하늘이 흐려 실제로 뿌옇게 찍혔고(박무·구름), 오후에 습도가 내려가자 높게 부르는 것도 사라졌다. 사람이 봐도 먼지 낀 날처럼 보인다
- **베이징(206일)에서는 확인됐다.** 기상 없는 모델은 습한 날을 모든 농도에서 5~15 높게 불렀고, 습도를 알려 주자 크게 줄었다.
  같은 사진에 습도만 바꿔 넣어 보니 **습하다고 할수록 예측을 낮추고, 뿌연 사진일수록 많이 낮췄다** — "뿌연 것의 일부는 습기"라고 보정하는, 처음 의도 그대로의 사용법이다
- **왜 인천에서는 안 됐나: 그런 날을 본 적이 거의 없어서.** 베이징에서 14일치만 주고 습도 보정을 배우게 하면 오히려 나빠지고, 100일 이상 주면 좋아진다(30번 반복 실험)
  - 10/14 보충: 습도 없이 "보정만" 붙여도 14일에서는 똑같이 나빠졌다(+0.5). 날이 적으면 무엇을 붙이든 그날들에만 맞는 규칙이 된다는 뜻이다.
    이 실험은 신경망을 다시 학습한 것이 아니라, 저장된 예측에 간단한 보정식을 붙여 본 것이다

### 고농도는 "그 카메라에서" 봐야 맞힌다 (2026-10-13)

- 인천의 '나쁨'(36 이상) 사진 94장은 두 버전 모두 하나도 맞히지 못했다(실제 평균 40을 21로). 베이징 '나쁨'은 114일을 봐서 85%를 맞힌다
- 베이징 고농도를 배운 인천+베이징 ver도 인천의 탁한 날은 인천 ver과 똑같이 낮게 불렀다. **다른 도시에서 본 고농도가 인천 카메라로 옮겨 오지 않았다**
- "도시를 외운 것"은 아닌 것으로 보인다. 모델 속 가장 큰 축은 두 도시 모두에서 "뿌연 정도"를 같은 눈금으로 잰다. 대신 **카메라마다 같은 농도에서 흐려지는 정도가 5배 넘게 달라**,
  그 카메라의 탁한 날을 직접 봐야 눈금을 맞출 수 있다. 인천은 그런 날이 3일뿐이었다
- 그래서 지금 "인천+베이징 ver이 인천 황사에 대비된다"고는 말할 수 없다. 확인된 것은 베이징 고농도다
- 4등급(좋음·보통·나쁨·매우나쁨)으로 바꾸면 인천 84%, 베이징 84%. 베이징에서 두 등급 이상 틀린 것은 4,123장 중 4장

**한 줄 요약: 모델은 그 카메라에서 그 상황(습한 아침, 탁한 날)을 여러 날 본 만큼 맞힌다. 인천의 한계는 수집 기간이 짧은 데서 오고, 수집이 이어지면 줄어들 문제다.**

### 최종 시험 결과 (2026-10-13)

모델을 다 고른 뒤, 한 번도 쓰지 않고 떼어 둔 시험지를 열었다. "익숙한 카메라의 처음 보는 날"을 맞히는 시험이다.

| | 시험지 A 인천 (4일) | 시험지 B 베이징 (67일) |
|---|---|---|
| 평균만 부르기 | 3.93 | — |
| **최종 인천 ver** | **2.46** (평균만보다 37% 적게 틀림) | 34.2 (베이징을 안 배움) |
| **최종 인천+베이징 ver** | **2.48** | **5.98** |

- 인천+베이징 ver은 베이징 고농도에서 평균 6 정도만 틀리고, 4등급으로 83%를 맞혔다. 습도를 넣어 7에서 6으로 줄어든 것이 시험지에서도 그대로 나왔다
- **주의할 점: 시험지 A는 4일뿐이고 쉬운 날(최대 33)이라, 단계별 모델이 모두 2.4~2.7로 비슷하게 나왔다.** 사진 없이 기상만 본 단순한 식도 2.61이 나왔다.
  그래서 "단계마다 좋아졌다"는 연습시험(14일) 표로 말하고, 시험지 A는 "처음 보는 날에서도 평균만보다 37% 적게 틀린다"로 말하는 것이 정직하다
- 인천의 탁한 날은 시험지 A에 없어서, 그 약점은 이 시험으로 확인되지 않는다
- **정답 자체도 흔들린다(10/14 확인).** 정답은 카메라에서 0.4~4km 떨어진 측정소 값이다. 몇 km 떨어진 측정소끼리 같은 시간 값을 비교하면 평균 3.4 차이가 난다.
  그래서 2.46은 "정답이 허락하는 정밀도"와 비슷한 크기이고, 이보다 0.1~0.2 좋아졌는지는 이 시험지로 가릴 수 없다
- 날별로 보면 4일 모두 평균만보다 나았다. 같은 시각의 20대 사이에서도 정답이 높은 카메라를 높게 불렀다(상관 0.50). 시간대·날씨만 보고 맞힌 게 아니라는 뜻이다

**속도.** 3060 Ti로 초당 약 90장을 배운다. 버전마다 후보 7개씩 다 돌리면 약 18~21시간(밤 두 번 정도).
**학습 중에는 게임을 끈다.** GPU를 같이 쓰면 몇 분의 1로 느려진다(실제로 겪음).

## 7. 외부 데이터 — 탁한 날을 배우게 하기

### 왜 필요한가

인천은 요즘 공기가 깨끗하다. 숭의 측정소 최근 3개월 중 '나쁨' 이상은 1.8%, '매우나쁨'은 0시간이다.
모델 마감까지 모이는 데이터는 사실상 **0~35㎍/㎥ 구간뿐**이다. 본 적 없는 고농도를 맞힐 수는 없다.
미세먼지 사건은 수백 km 규모라 인천 안에서 카메라를 옮겨도 해결되지 않는다.

그래서 **다른 지역의 고농도 사진 데이터셋**을 구했다.

| 데이터 | 내용 |
|---|---|
| 허산(중국) | 306장, 11~100㎍/㎥. 폰으로 찍은 사진이라 학습에는 안 쓰고, 고농도에서도 가설이 통하는지 확인하는 참고용 |
| 베이징 | 고정 카메라 1대, 30분 간격, 9개월 반(약 1만 3천 장). 낮 시간 중 75 초과가 353시간, 150 초과가 101시간. **학습에 쓴다** |

### 어떻게 섞나

인천 단독 결과를 기준점으로 먼저 만든 뒤 비교한다.

| 방식 | 판단 |
|---|---|
| 인천 → 외부 순서로 학습 | 안 쓴다. 마지막에 본 쪽으로 쏠려 인천을 보는 능력이 떨어질 수 있다 |
| 외부 → 인천 순서로 학습 | 해 본다 |
| 섞어서 한 번에 | 해 본다 |

**시험지 A(인천) 점수가 나빠지지 않으면서 시험지 B(고농도) 점수가 좋아지는 쪽**을 고른다.

→ **2026-10-11에 바꿨다.** 하나를 고르지 않고 **인천 ver과 인천+베이징 ver(섞어서)을 둘 다 남긴다**(§6).
"외부 → 인천" 순서는 뺐다. 마지막에 인천(저농도)만 보며 마무리하는 동안 베이징에서 배운 고농도 감각을 잊을 수 있어서,
고농도 대비라는 인천+베이징 ver의 목적과 맞지 않는다.

### 함정: 도시를 외우는 모델

외부에 탁한 사진만, 인천에 맑은 사진만 있으면 모델이 뿌연 정도가 아니라
**"베이징 건물이면 높고, 인천 건물이면 낮다"**를 외울 수 있다. 점수는 좋아 보여도 쓸모없는 모델이다.
그래서 외부 데이터도 **같은 카메라 안에 맑은 날과 탁한 날이 함께** 있어야 한다.
베이징은 매달 맑은 시간과 탁한 시간이 같이 있어서 이 조건을 만족한다(2026-10-10 확인).
같은 이유로 **계절**도 조심한다. 베이징은 겨울에 탁하고 나무가 앙상해지는데, 모델이 "나무가 앙상하면 높다"를 외우지 않게 하늘·먼 건물만 보게 한다.

외부 데이터를 결국 못 쓰게 되면 **"0~35 범위에서 검증"을 한계로 밝힌다.** 그래도 결과물은 완성된다.

## 8. 완성되면 어떻게 쓰이나

```
[VM]  수집기 (그대로)   → 20분마다 사진
      추정기 (별도)     → 카메라 20대 추정값 → 백엔드
[백엔드 + DB] → 프론트 타임라인 (추정값 + 나중에 채워지는 실측값)
[로컬] 주 1회 정도 재학습 → 시험 점수가 나을 때만 VM 모델 교체
```

- **수집할 때마다 학습은 못 한다.** 정답(1시간 평균)이 약 1시간 뒤에 게시되므로, 찍는 순간에는 학습할 짝이 없다
- **추정기를 수집기와 따로 둔다.** 추정 쪽에서 오류가 나도 수집이 멈추지 않게 하려는 것이다. 놓친 사진은 다시 구할 수 없다
- **밤**에는 사진이 없으므로 측정소 실측값을 지도 위에 보간(IDW)해 보여 주고, 낮(CCTV 추정)과 구분해 표시한다
- 모델 값과 보간 값은 에어코리아 값이 아니라 **"우리가 계산한 값"으로 표시**한다

## 10. 자주 묻는 질문

**Q. 정답(PM2.5)이 없는 사진도 있나?**
있다. 측정소에서 서버로 값이 전송되지 않으면(통신장애) 그 시간 값이 `-`로 온다. 9/22~10/9에 86시간이었다.
그 시간 사진은 앞뒤 값으로 메우지 않고 뺀다(§2).

**Q. 베이스라인은 사진을 안 보고 맞힌 건가?**
아니다. 베이스라인도 사진을 보지만, **사람이 정한 숫자 13개만** 본다. CNN은 무엇을 볼지 스스로 찾는다(§5, §6).

**Q. 같은 시간 사진 3장이 정답을 공유하면 문제 아닌가?**
정답이 원래 1시간 평균이라 어쩔 수 없다. 대신 채점할 때 **같은 카메라·같은 1시간 사진 3장의 예측을 평균**해
1시간 정답과 비교하는 방식도 같이 본다.

**Q. 평균 쪽으로 쏠리는 건 놔둬도 되나?**
베이스라인 자체는 놔둔다. 다만 원인이 데이터 부족이면 CNN에서도 똑같이 나오므로 원인은 짚어 둔다(§5 약점).

**Q. 시험지 A는 왜 한 번만 보나?**
보고 나서 방법을 고치면 시험지가 연습 문제가 되어 점수가 부풀려진다. 모델을 다 고른 뒤 맨 끝에 한 번 본다(§4).

**Q. CNN은 왜 그렇게 예측했는지 설명이 불가능한가?**
완전히 불가능하진 않다. 사진의 어느 부분을 봤는지는 열 지도로 보여 줄 수 있다. 다만 숫자가 나온 이유를 공식처럼 풀 수는 없다(§6).

**Q. 데이터가 1만 장이면 충분한가?**
장수보다 날짜 수가 중요하다. 같은 날 사진은 대기 상태가 같아서, 1만 장이어도 "19번의 경험"에 가깝다(§2).
그래서 수집은 1월까지 계속한다.

|---|---|---|
| **라벨** (정답) | 모델이 맞혀야 할 답 | 에어코리아 PM2.5 1시간 값 |
| **특징** (feature) | 모델에 넣는 숫자 하나하나 | 대비, 채도, 암채널, 습도 … |
| **거르기** | 학습에 해로운 데이터 빼기 | 비, 고습도, 결측 |
| **결측** | 값이 비어 있음 | 메우지 않고 뺀다 |
| **실질 표본** | 서로 독립적인 데이터 수 | 사진 수가 아니라 날짜 수에 가깝다 |
| **ROI** | 사진에서 볼 영역 (Region Of Interest) | 하늘·먼 건물 |

### 모델

| 용어 | 뜻 | 비유 |
|---|---|---|
| **모델** | 입력을 넣으면 답을 내놓는 계산 장치 | 시험 보는 학생 |
| **학습** | 정답을 보며 계산법을 맞춰 가는 것 | 공부 |
| **회귀** | 숫자를 맞히는 문제. 고르는 문제는 "분류" | "몇 점일까" 맞히기 |
| **가중치** | 모델 안의 숫자. 학습으로 정해진다 | "암채널이 0.1 오르면 PM2.5가 2 오른다" |
| **Ridge 회귀** | 가장 단순한 회귀(특징마다 점수를 매겨 더하는 공식)에 과적합 방지 장치를 단 것 | 베이스라인에 쓴 방법 |
| **과적합** | 공부한 문제는 잘 푸는데 새 문제는 못 푸는 상태 | 답을 외운 학생 |
| **규제** (alpha) | 과적합을 막는 손잡이. 세면 조심스럽게 예측한다 | 우리 데이터는 충분히 많아 거의 영향이 없었다 |
| **부스팅** | 작은 판단 규칙을 여러 개 쌓는 방식. 직선이 아닌 관계도 잡는다 | 베이스라인에서 시험 삼아 돌려 봄 |
| **베이스라인** | 비교 기준이 되는 단순한 모델 | ③단계 |
| **CNN** | 사진을 직접 보는 딥러닝 모델 (합성곱 신경망) | ④단계 |

### CNN

| 용어 | 뜻 |
|---|---|
| **사전학습** | 남이 일반 사진 수백만 장으로 미리 가르쳐 둔 모델. "사진 보는 눈"이 이미 있다 |
| **미세조정** | 사전학습 모델을 우리 데이터로 조금 더 가르쳐 PM2.5용으로 바꾸는 것 |
| **백본** | CNN에서 사진을 보는 몸통. 우리는 ConvNeXt V2-Tiny |
| **회귀 헤드** | 백본 끝에 붙여 숫자 하나(PM2.5)를 내놓게 하는 작은 부분 |
| **증강** | 사진을 뒤집고 밝기를 바꿔 문제집을 늘리는 기법. **우리는 색·밝기 증강 금지** |
| **전이학습** | 다른 데이터로 배운 것을 우리 문제에 옮겨 쓰는 것 |
| **Grad-CAM** | CNN이 사진의 어디를 보고 판단했는지 색칠해 보여 주는 도구 |
| **에폭(바퀴)** | 학습 사진 전체를 한 바퀴 보는 것. 너무 많이 돌면 학습 사진을 외운다 |
| **묶음(배치)** | 한 번에 같이 계산하는 사진 수. 우리는 16장 (8GB GPU에 들어가는 만큼) |
| **로그 변환** | 숫자를 "몇 배인가"의 눈금으로 바꾸는 것. 10→15와 200→300이 같은 크기의 차이가 된다 |
| **혼합 정밀도** | 계산 일부를 가벼운 숫자 형식으로 해 빠르게 하는 기법. 결과 차이는 거의 없다 |

### 평가

| 용어 | 뜻 | 예 |
|---|---|---|
| **MAE** | 평균 오차. 틀린 크기를 평균 낸 것 | 4.8이면 "보통 4.8㎍/㎥쯤 틀린다" |
| **RMSE** | MAE와 비슷하지만 크게 틀린 것에 벌점을 더 준다 | 크게 틀리는 날이 있으면 MAE보다 커진다 |
| **개선폭** | 평균만 부르는 모델보다 오차가 몇 % 줄었나 | 이미지+기상 23% |
| **날짜 단위 분할** | 공부용과 시험용을 날짜로 나눔 | 같은 날 사진이 양쪽에 걸치면 점수가 부풀려진다 |
| **교차검증** | 돌아가며 시험용으로 써서 점수를 여러 번 내 평균 내기 | 베이스라인은 14일 중 하루씩 빼고 14번, CNN은 날짜 3묶음으로 3번 |
| **시험지 A** | 끝까지 숨겨 두는 최종 시험 (인천) | 9/22부터 4일마다 하루 |
| **시험지 B** | 고농도 참고 시험 (외부 데이터) | 베이징 첫날부터 4일마다 하루 (67일) |
| **상관** (r) | 두 값이 같이 움직이는 정도. 1이면 완벽, 0이면 무관 | 베이스라인 예측과 정답 r = 0.51 |
| **쏠림** | 예측이 평균 쪽으로 몰리는 현상 | 탁한 날을 낮게 맞힘 |

### 카메라 차이 다루기

카메라마다 장면이 달라서, 하늘이 넓은 카메라는 평소 암채널이 0.6, 건물이 많은 카메라는 0.2일 수 있다.
숫자 크기를 그대로 비교하면 안 되고 **"그 카메라 평소보다 얼마나 변했나"**를 봐야 한다.

| 용어 | 뜻 |
|---|---|
| **표준화** | 숫자를 "평소보다 얼마나 높은가"로 바꾸는 것 |
| **카메라 번호** (더미, 원-핫) | "몇 번 카메라인가"를 모델에 알려 주는 것. 동네마다 평소 농도가 다른 것을 흡수한다 |

베이스라인 성적표에는 두 가지를 조합한 방식 셋이 나란히 나온다. 카메라 번호를 넣는 두 방식이 비슷하게 좋았고(4.81·4.86),
표준화만 한 방식은 뒤졌다(5.05). 동네 정보가 빠지기 때문이다.
